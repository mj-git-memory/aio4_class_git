# note-demo 구현을 위한 AI 에이전트 프롬프트

당신은 요구사항 분석부터 구현, 실행 확인까지 담당하는 소프트웨어 개발 AI 에이전트다. 아래 설계에 따라 `note-demo` 프로젝트를 완성하라. 설명이나 구현 계획만 제시하고 끝내지 말고, 실제 파일을 작성하고 실행 가능한 결과를 제공하라.

## 1. 기준과 작업 방식

- 원본 설계는 같은 디렉터리의 `prompt.md`다. 먼저 읽고 아래 요구사항과 함께 확인하라. 명시된 사용자 요구사항이 이 문서의 기본 가정보다 우선한다.
- 기존 파일, 프로젝트 설정, `AGENTS.md` 등 적용되는 지침을 확인하고 기존 구조와 기술 스택을 존중하라. 기존 사용자 작업을 덮어쓰지 마라.
- 후속 사용자 피드백에 따라 **PythonAnywhere 무료 계정 배포**를 기준으로 한다. 기술 스택은 Python + Flask + SQLite + Jinja2 + 기본 HTML/CSS/JavaScript로 하고, 상세 구현 순서와 배포 지침은 `plan.md` 최종본을 함께 읽어라. Node.js·Vite 빌드나 별도 서버 프로세스 없이 호스팅 WSGI로 실행하라.
- 아래에서 ‘필수’로 정한 사항을 모두 구현하라. ‘기본 가정’은 원본에 없는 빈칸을 채우기 위한 결정이며 새로운 확정 요구사항으로 취급하지 마라. 다른 결정이 필요하면 근거와 함께 기록하라.
- 일반적인 구현 선택은 스스로 진행하되, 요구사항이 충돌하거나 작업을 막는 정보가 부족할 때만 구체적으로 질문하라.
- 한국어 화면과 안내 문구를 사용하라. 불필요한 기능을 늘리기보다 필수 사용자 흐름을 완성하라.

## 2. 프로젝트 목적과 범위

프로젝트 이름은 `note-demo`다. 회원가입과 로그인으로 사용자를 구분하고, 본문만 작성하는 방명록에 글과 댓글을 남길 수 있는 데모를 만든다. 불쾌한 표현은 관리자가 관리하는 키워드 및 정규식 규칙을 통해 화면에서 마스킹한다.

### 현재 구현할 필수 기능

1. 이메일, 이름 또는 닉네임, 비밀번호를 입력하는 목업 회원가입
2. 로그인과 로그아웃
3. 비밀번호 찾기 목업 화면 및 동작 안내
4. 방명록 작성, 페이지 단위 목록, 본문 내 상세 펼침
5. 본인 방명록 글 수정 및 삭제
6. 글별 댓글 작성 및 조회
7. 불쾌한 표현 마스킹과 관리자 규칙 추가 및 삭제
8. 최소 화면 구성과 데이터 관계 설계: ERD 및 데이터베이스 테이블 구조 문서화

### 향후 기능 — 현재 실제 서비스 연동을 구현하지 않음

- 회원가입·로그인을 SNS 로그인으로 대체
- SNS 계정 연결, 이메일 소유 확인 등 운영용 인증 체계 확장. 단, 공개 배포에 맞춰 비밀번호 해시 저장·검증은 이번 구현에 포함한다.
- 이메일 발송 및 재설정 링크를 사용하는 실제 비밀번호 찾기

현재 화면에서 실제 이메일 발송이나 운영 수준의 인증이 완료된 것처럼 표현하지 마라. 데모 계정 기능임을 알리고 실제 서비스에서 쓰는 비밀번호 입력을 권하지 마라. 공개 배포를 고려해 Werkzeug 등 검증된 함수로 해시 저장·검증하고 평문 비밀번호를 저장하거나 콘솔·로그·조회 응답에 노출하지 마라.

## 3. 원본에 없는 사항의 기본 가정

다음은 질문 없이 개발을 진행하기 위한 기본값이다. 최종 README에 채택한 가정을 명시하라.

- 비로그인 사용자도 방명록 목록, 상세 내용, 댓글을 읽을 수 있다. 글과 댓글 작성은 로그인한 사용자만 가능하다.
- 댓글은 단일 단계로 구현한다. 대댓글, 댓글 수정·삭제는 필수 범위에 포함하지 않는다.
- 방명록은 최신 작성 순으로 표시한다. 댓글은 작성 순으로 표시한다.
- 제목 입력란은 만들지 않는다. 작성자와 작성 시각은 보조 정보로 표시할 수 있다.
- 사용자·글·댓글·마스킹 규칙은 서버의 SQLite DB에 저장하고 브라우저·기기 간 공유한다. localStorage나 sessionStorage를 계정·데이터 저장소로 사용하지 않는다.
- 관리자 역할을 구분하고 관리자로 데모에 진입할 방법을 제공한다. 일반 회원가입으로 관리자 권한을 선택할 수 없게 한다.
- 로그인 사용자는 Flask의 서명된 세션 쿠키로 식별한다. 사용자 ID만 세션에 담고 역할·소유권은 서버의 DB 조회로 검사한다. 세션은 암호화된 저장소가 아니므로 비밀값을 담지 마라.

## 4. 기능별 상세 요구사항

### 4.1 회원가입·로그인·로그아웃

- 회원가입 필드는 이메일 주소, 이름 또는 닉네임, 비밀번호다.
- 비밀번호는 후속 사용자 요청에 따라 최소 6자, 최대 128자로 한다. 서버 검증·회원가입 및 로그인 화면·관리자 생성 CLI에 동일하게 적용하고 기존 비밀번호를 임의로 변경하지 마라.
- 필수값 누락, 잘못된 이메일 형식, 이메일 중복을 검사하고 이해하기 쉬운 오류 메시지를 보여라.
- 등록한 목업 계정으로 로그인할 수 있어야 한다. 잘못된 자격 증명으로는 로그인되지 않아야 한다.
- 로그인 상태와 현재 사용자 정보를 일관되게 관리하고, 로그아웃하면 작성·수정·삭제 권한을 즉시 해제하라.
- 비밀번호 찾기는 접근 가능한 화면과 입력·안내 흐름을 제공하되, 실제 발송 기능이 없는 목업임을 명시하라. 기존 비밀번호를 보여주지 마라.

### 4.2 방명록 작성·목록·페이징

- 글 입력은 본문만 받는다. 비어 있거나 공백만 있는 글은 저장하지 마라.
- 목록에서 본문 전체를 노출하지 말고 약 10글자의 미리보기로 표시하라. 기본 구현은 10글자까지 표시하고 초과하면 말줄임표를 붙인다.
- 한 페이지의 기본 글 수는 10개다. 실제 데이터에 따라 페이지 수를 계산하고 페이지를 이동하면 해당 페이지의 글을 보여라.
- 글 수가 0개, 1개, 10개, 11개 이상일 때 모두 정상 동작해야 한다.
- 글 삭제 등으로 현재 페이지가 사라지면 유효한 마지막 페이지로 이동하라. 글이 없을 때는 빈 상태 안내를 표시하라.
- 글 작성 후 새 글과 목록을 바로 확인할 수 있게 하라.

### 4.3 방명록 상세 내용

- 목록의 글을 클릭하면 전체 본문을 확인할 수 있어야 한다.
- **팝업, 모달, 새 창, 별도 상세 페이지로 표시하지 마라.**
- **현재 페이지 body 안에 미리 숨겨 둔 상세 영역을 펼쳐서 표시하라.** 예를 들어 목록 아래의 `hidden` 상세 영역을 선택 시 해제하는 방식이다.
- 다른 글을 선택하면 해당 영역의 본문과 댓글을 선택한 글 기준으로 갱신하라. 상세 영역을 다시 닫을 수 있게 하라.
- 본문 줄바꿈을 유지하고, 상세 펼침 동작은 키보드로도 사용할 수 있게 하라.

### 4.4 본인 글 수정·삭제

- 현재 사용자의 ID와 글 작성자의 ID가 일치할 때만 수정·삭제를 허용하라. 닉네임 문자열로 소유권을 판단하지 마라.
- 다른 사용자의 글과 비로그인 상태에서는 수정·삭제 버튼을 제공하지 않는다.
- 버튼 숨김 외에도 실제 수정·삭제 요청을 처리하는 서버 로직에서 소유권을 검사하라. 본인 수정용 원문을 반환하는 요청에도 같은 검사를 적용하라.
- 수정 결과는 목록 미리보기와 열린 상세 내용에 즉시 반영하라. 수정에서도 공백 본문을 거부하고 마스킹을 적용하라.
- 삭제 실수를 방지할 확인 단계를 제공하고, 삭제한 글이 열려 있으면 상세 영역과 댓글 표시를 정리하라.

### 4.5 댓글

- 각 댓글을 특정 방명록 글의 ID에 연결하라. 다른 글의 댓글이 섞이지 않아야 한다.
- 로그인한 사용자가 상세 영역에서 댓글을 작성하고 해당 글의 댓글을 조회할 수 있어야 한다.
- 빈 댓글과 공백만 있는 댓글은 거부하라. 저장 후 댓글 목록을 즉시 갱신하라.
- 글 삭제 시 연결된 댓글도 함께 정리하라.

### 4.6 불쾌한 표현 탐지·마스킹

- 키워드 매핑과 정규식 형태의 규칙을 지원하라. 각 규칙은 고유 ID, 유형, 패턴 및 필요한 옵션을 갖도록 구성하라.
- 일치하는 표현만 `*` 등으로 가리고 나머지 문장은 유지하라. 같은 문장에 여러 번 등장하거나 여러 규칙이 일치해도 누락 없이 처리하라.
- **목록 미리보기, 상세 본문, 댓글의 모든 사용자 본문 표시 경로에 동일한 마스킹 처리를 적용하라.**
- 목록 미리보기는 전체 본문에 마스킹을 적용한 뒤 10글자로 잘라라. 잘린 표현 때문에 마스킹이 누락되지 않게 하라.
- 일반 키워드는 정규식 메타문자를 문자 그대로 취급하라. 관리자가 정규식 유형으로 등록한 경우에만 정규식으로 해석하라.
- 잘못된 정규식은 저장 전에 검증해 오류를 알리고, 앱 전체가 중단되지 않게 하라. 지나치게 복잡하거나 위험한 패턴의 처리 방침도 정하라.
- 원문과 화면 표시를 위한 마스킹 결과를 구분하라. 규칙 변경 후 기존 글과 댓글에도 최신 규칙이 적용되어야 하고, 본인 글 수정 시 원문을 편집할 수 있어야 한다.
- 마스킹은 서버에서 응답 전에 수행하라. 목록 HTML·읽기용 JSON에 마스킹 전 원문을 숨겨 전달하지 마라. 정규식은 시간 제한을 지원하는 Python `regex` 등으로 처리하고 패턴·본문·규칙 수와 전체 처리 시간도 제한하라. 시간 초과 시 원문 대신 대체 안내를 표시하라. 별도 Worker·상시 프로세스는 도입하지 마라.
- 본문을 HTML로 직접 삽입하지 말고 안전한 텍스트로 렌더링하라.

### 4.7 최초 규칙 구성과 관리자 관리

- **구현 시점에 인터넷에서 최신 정보를 실제로 조사하여** 초기 규칙을 구성하라. 이번 프롬프트 작성 시점에 조사를 마친 것으로 가정하지 마라.
- 공개된 한국어 유해 표현 관련 자료, 공개 사전 또는 공개 프로젝트 등에서 출처와 이용 조건을 확인하라. 단순 문자열 매칭의 오탐·누락 가능성을 검토해 데모에 적합한 초기 규칙을 선택하라.
- 조사 결과의 출처 URL, 확인 날짜, 선택 기준과 한계를 README 또는 별도 출처 문서에 기록하라. 최신 정보 조사 없이 ‘최신 목록’이라고 주장하지 마라.
- 네트워크나 접근 제한으로 조사를 완료하지 못하면 이를 명시하고, 임시 규칙과 검증된 규칙을 구분하라. 조사 요구사항을 완료했다고 보고하지 마라.
- PythonAnywhere 무료 계정의 외부 요청 제한을 고려해 초기 규칙은 개발 중 조사하고 파일로 함께 배포하라. 앱 실행·초기화 과정에서 인터넷 조사·API 호출·예약 작업에 의존하지 마라.
- 관리자가 규칙 목록을 조회하고 키워드 또는 정규식 규칙을 추가·삭제할 수 있는 관리 화면을 구현하라.
- 빈 패턴과 동일 유형·패턴·옵션의 중복 규칙을 처리하라. 일반 사용자가 관리 동작을 실행하지 못하도록 화면과 처리 로직에서 권한을 검사하라.
- 관리자 변경은 저장되고 새로고침 후에도 유지되어야 한다. 초기 규칙은 최초 초기화에만 넣어라. 관리자가 삭제한 초기 규칙이 새로고침 때 복원되면 안 된다.
- 규칙 추가·삭제 후 이미 표시 중인 글과 댓글도 최신 마스킹 결과로 갱신하라.
- 변경한 브라우저는 즉시 다시 조회해 갱신하고, 다른 사용자의 화면은 다음 조회·새로고침 시 적용한다. 실시간 푸시는 이번 범위에 포함하지 않는다.

## 5. 데이터 및 화면 구성 지침

### 5.1 최소 화면 구성

- **화면은 간단명료하게 구성하라.** 핵심 작업을 쉽게 찾을 수 있도록 짧고 명확한 메뉴와 버튼을 사용하고, 불필요한 화면 분리나 장식은 줄여라.
- 최소 화면 구성표를 작성하고 각 화면 또는 영역의 목적, 접근 권한, 주요 입력값, 주요 동작을 명시하라. 화면별 기능과 실제 구현이 일치해야 한다.
- 회원가입, 로그인, 비밀번호 찾기 목업, 방명록 목록·작성·숨김 상세 영역, 관리자 규칙 관리를 포함하라. 로그인 상태와 로그아웃 동작도 화면 구성에 표시하라.
- 방명록 상세 본문과 댓글은 현재 body의 숨김 영역에서 제공하라. 화면 구성표에서 상세 내용을 별도 페이지나 팝업으로 설계하지 마라.
- 목록, 상세 내용, 댓글, 인증 상태, 페이지 번호가 서로 어긋나지 않게 상태를 관리하라.
- 입력 필드에 레이블을 제공하고, 버튼 역할과 오류·빈 상태 안내를 명확히 하라. 작은 화면에서도 사용할 수 있게 하라.

### 5.2 데이터 관계와 ERD

- 사용자, 방명록 글, 댓글, 마스킹 규칙을 각각 구분하고 안정적인 ID로 연결하라. 글과 댓글의 작성자는 로그인 정보에서 결정하며 입력값으로 임의 지정하지 못하게 하라.
- **데이터 관계를 Mermaid `erDiagram` 형식의 ERD로 작성하라.** 엔터티 이름만 나열하지 말고 주요 필드, 기본 키, 외래 키, 관계의 방향과 개수(1:N 등)를 표현하라.
- 최소한 사용자(`users`), 방명록 글(`posts`), 댓글(`comments`), 마스킹 규칙(`masking_rules`)을 포함하라. 이름은 기존 프로젝트에 맞춰 바꿀 수 있으나 역할은 유지하라.
- 사용자와 작성 글, 사용자와 작성 댓글, 글과 댓글의 1:N 관계를 명시하라. 규칙 작성자 등 추가 관계는 실제 저장하는 경우에만 표현하라. 마스킹 규칙은 콘텐츠에 공통 적용되며, 단지 마스킹에 사용된다는 이유로 글마다 외래 키를 만들지 마라.

### 5.3 데이터베이스 테이블 구조

- **각 테이블의 구조를 표로 명시하라.** 컬럼명, 데이터 타입, NULL 허용 여부, 기본값, PK/FK, UNIQUE 등 제약조건, 설명을 포함하라.
- 최소 필드는 다음 역할을 충족해야 한다. 구체적인 타입과 이름은 선택한 저장 방식에 맞춰 정하고 ERD·문서·구현에서 일치시켜라.
  - 사용자: ID, 이메일, 이름 또는 닉네임, 목업 인증 정보, 사용자 역할, 생성 시각
  - 방명록 글: ID, 작성자 ID, 본문 원문, 생성 시각, 수정 시각
  - 댓글: ID, 글 ID, 작성자 ID, 본문 원문, 생성 시각
  - 마스킹 규칙: ID, 유형, 패턴, 정규식 옵션, 생성 시각
- 이메일 중복 방지, 작성자와 글의 참조 무결성, 글 삭제 시 댓글 정리, 규칙 중복 방지 정책을 명시하라. 페이징 조회와 글별 댓글 조회에 필요한 인덱스도 설명하라.
- SQLite에서 실행 가능한 스키마 SQL과 향후 변경을 적용할 방식을 제공하라. 외래 키를 연결마다 활성화하고 글 삭제 시 댓글 CASCADE, 이메일·규칙 UNIQUE, 역할 CHECK와 조회 인덱스를 반영하라. 매개변수 바인딩으로 SQL을 실행하라.
- DB는 정적 공개 디렉터리 밖의 `instance`에 저장하고 절대 경로로 연결하라. 재시작 시 DB를 재생성하지 말고, 최초 시드와 스키마 변경은 명시적 CLI로 처리하라.
- 현재 비밀번호 해시 필드를 명시하라. 현재 구현에 없는 SNS 계정 연결이나 재설정 토큰 테이블을 이미 구현한 것처럼 기술하지 마라.
- 저장 데이터가 없을 때와 잘못된 저장 데이터를 읽었을 때 처리 방침을 마련하라. 목업 데이터를 실제 회원 데이터처럼 설명하지 마라.
- 화면 구성표, ERD, 테이블 구조는 `docs/design.md`에 저장하고 README에서 링크하라. 기존 설계 문서 위치가 있다면 그 형식을 따르되 동일한 내용을 빠짐없이 포함하라.

### 5.4 PythonAnywhere 무료 배포

- 신규 무료 계정에서 MySQL이 제공된다고 가정하지 말고 SQLite를 사용하라. 상세 한도와 공식 근거는 `plan.md`를 확인하고 배포 시 실제 계정 상태를 재확인하라.
- `requirements.txt`, WSGI `application` 진입점, 가상환경·Manual configuration·정적 파일 매핑·Reload 절차를 제공하라. 배포에는 Flask 개발 서버를 사용하지 마라.
- SECRET_KEY 등 비밀 설정을 코드·Git 밖에서 명시적으로 로드하고 HTTPS 세션 쿠키를 설정하라. 데이터 변경·로그아웃 요청에 CSRF 보호를 적용하고 debug는 끄도록 하라.
- 관리자는 전용 CLI에서 생성하고 공개된 기본 비밀번호를 배포하지 마라.
- 브라우저 Worker, Node.js 상시 서버, Redis·Celery·예약 작업, 외부 DB와 이메일 발송 의존성은 추가하지 마라. CSS·JS는 로컬 정적 파일로 제공하라.
- 무료 앱 만료일 확인·연장, 디스크 사용량 점검, DB 백업·복원을 README에 설명하라. DB·설정 디렉터리를 정적 파일로 매핑하지 마라.

## 6. 완료 조건과 검증

적절한 수준의 자동 검증과 실제 실행 확인을 수행하라. 아래 항목별로 확인 결과를 기록하고, 실행하지 못한 것은 ‘미확인’으로 구분하라.

- [ ] 필수 입력값·이메일 형식·이메일 중복 검사와 회원가입이 동작한다.
- [ ] 등록 계정 로그인, 잘못된 로그인 거부, 로그아웃 후 권한 해제가 동작한다.
- [ ] 비밀번호 찾기 화면이 목업임을 명확히 안내한다.
- [ ] 제목 없이 본문만으로 글을 작성하며 공백 글을 거부한다.
- [ ] 목록은 마스킹된 본문 약 10글자만 표시한다.
- [ ] 0개·1개·10개·11개 이상 데이터와 마지막 페이지 삭제에서 페이징이 정상 동작한다.
- [ ] 클릭한 글의 전체 본문이 현재 body의 숨김 영역에 펼쳐지며 팝업이나 페이지 이동을 사용하지 않는다.
- [ ] 사용자 두 명으로 확인했을 때 본인 글만 수정·삭제할 수 있고, 처리 로직에서도 권한을 검사한다.
- [ ] 글별 댓글 작성·조회가 동작하고 서로 다른 글의 댓글이 섞이지 않는다.
- [ ] 키워드·정규식·반복 출현·여러 규칙 일치 사례에서 목록·상세·댓글에 일관되게 마스킹된다.
- [ ] 잘못된 정규식과 공백 입력을 처리해도 앱이 중단되지 않는다.
- [ ] 관리자만 규칙을 추가·삭제할 수 있으며 일반 회원은 해당 동작을 수행할 수 없다.
- [ ] 규칙 변경이 기존 콘텐츠와 현재 화면에 반영되고 새로고침 후에도 유지된다.
- [ ] 초기 규칙 조사 출처와 확인 날짜가 기록되어 있다. 조사 불가 시 미완료 사실이 명시되어 있다.
- [ ] HTML처럼 보이는 글과 댓글이 코드 실행 없이 텍스트로 표시된다.
- [ ] 선택한 저장 방식으로 새로고침 후 사용자·글·댓글·규칙 데이터가 의도대로 유지된다.
- [ ] 간단명료한 최소 화면 구성표가 있으며 접근 권한과 주요 동작이 실제 화면과 일치한다.
- [ ] Mermaid ERD에 사용자·글·댓글·마스킹 규칙, 주요 키와 관계의 개수가 표현되어 있다.
- [ ] 테이블별 컬럼·타입·NULL·기본값·키·제약조건·인덱스가 문서화되고 ERD 및 실제 데이터 모델과 일치한다.
- [ ] SQLite 스키마·제약·인덱스와 서버의 데이터 모델이 일치하고 WSGI Reload 후에도 데이터가 유지된다.
- [ ] 서버의 소유권·역할·CSRF 검사, 해시 저장, 원문 응답 제한, 배포용 쿠키·비밀 설정을 검증했다.
- [ ] PythonAnywhere 무료 환경의 WSGI·가상환경·정적 경로·DB 절대 경로와 앱 연장 절차를 문서화했다. 실제 원격 확인이 없으면 미확인으로 표시했다.
- [ ] 프로젝트의 실행 및 빌드 등 해당 스택에 필요한 기본 검증을 완료했다.

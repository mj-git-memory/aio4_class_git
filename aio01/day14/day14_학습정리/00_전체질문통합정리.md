## 1. Redis는 무엇인가요?

**Redis는 데이터를 주로 메모리에 저장하고 빠르게 읽고 쓰는 별도의 저장소 서버**입니다. 이름표인 키(key)로 값(value)을 찾습니다.

```text
키                 값
user:1:name        민수
product:10:stock   50
```

Python 딕셔너리와 비슷하지만 다른 프로그램들도 같은 Redis 서버에 접속해 공유할 수 있습니다. 임시 정보의 유효기간을 지정하거나 반복 조회 결과를 캐시하는 데 활용합니다. Redis에는 디스크 기록 기능도 있지만 보존 여부는 설정에 달려 있습니다.

## 2. Docker는 무엇인가요? 이미지와 컨테이너도 만드나요?

**Docker는 이미지를 만들고, 이미지로 컨테이너를 생성·실행·관리하는 도구**입니다.

| 개념 | 뜻 | 비유 |
|---|---|---|
| Dockerfile | 이미지 제작 방법을 적은 파일 | 조리 설명서 |
| 이미지 | 프로그램·필요 파일을 담은 실행 패키지 | 재료를 담은 밀키트 |
| 컨테이너 | 이미지를 바탕으로 만든 실행 공간 | 실제 요리하는 작업 공간 |

```text
Dockerfile → 이미지 만들기 → 컨테이너 생성·실행
```

이미지는 항상 직접 만들 필요가 없습니다. 이 수업은 이미 만들어진 `redis:7.4` 이미지를 사용합니다. 하나의 이미지로 여러 컨테이너를 만들 수 있습니다.

Docker를 사용하면 Redis를 직접 설치하고 설정하는 부담을 줄이고, 다른 사람도 비슷한 실행 환경을 준비하기 쉽습니다. 지금은 Python이 Mac에서 실행되고 Redis만 Docker 안에서 실행됩니다.

## 3. Redis 실행 명령 전체를 해석하면?

```bash
docker run -d --name kdt-redis -p 127.0.0.1:6379:6379 redis:7.4 redis-server --save "" --appendonly no
```

| 부분 | 의미 |
|---|---|
| `docker` | Docker 프로그램 사용 |
| `run` | 새 컨테이너를 만들고 실행 |
| `-d` | 백그라운드 실행 |
| `--name kdt-redis` | 컨테이너 이름 지정 |
| `-p 127.0.0.1:6379:6379` | Mac 내부 주소의 6379 포트와 컨테이너의 6379 연결 |
| `redis:7.4` | Redis 이미지 7.4 태그. 로컬에 없으면 다운로드 |
| `redis-server` | 컨테이너 안에서 실행할 Redis 서버 프로그램 |
| `--save ""` | RDB 자동 스냅샷 저장 끄기 |
| `--appendonly no` | AOF 변경 기록 저장 끄기 |

주소는 건물 주소, 포트는 그 건물의 창구 번호라고 생각하면 됩니다. `127.0.0.1`은 현재 컴퓨터 자신을 뜻합니다. [Docker 포트 연결 안내](https://docs.docker.com/get-started/docker-concepts/running-containers/publishing-ports/)에서 호스트·컨테이너 포트의 순서를 확인할 수 있습니다.

이 명령은 **내 Mac에서 접속할 실습용 Redis를 새로 실행하며, 데이터를 디스크에 남기지 않도록 설정**합니다. 중지·재시작하면 메모리 데이터는 사라집니다. 이미지가 있다는 것과 데이터가 보존된다는 것은 다른 이야기입니다.

## 4. PING과 버전 확인 명령은 무엇인가요?

```bash
docker exec kdt-redis redis-cli PING
```

`exec`는 실행 중인 컨테이너 안에서 추가 명령을 실행합니다. `kdt-redis`는 대상 컨테이너, `redis-cli`는 Redis에 명령하는 프로그램, `PING`은 응답 확인 요청입니다. 정상 응답은 `PONG`입니다.

```bash
docker exec kdt-redis redis-server --version
```

이번에는 컨테이너 안의 `redis-server`를 `--version` 옵션으로 실행해 버전을 출력합니다. 서버를 추가로 실행하는 명령이 아닙니다.

| 명령 | 확인하는 것 |
|---|---|
| `docker --version` | Mac의 Docker CLI 버전 |
| `docker exec kdt-redis redis-server --version` | 컨테이너의 Redis 프로그램 버전 |
| `docker exec kdt-redis redis-cli PING` | Redis가 실제 요청에 응답하는지 |

여기서 각각의 단어는 Python 함수가 아니라 프로그램 이름·하위 명령·대상·옵션입니다.

## 5. redis-cli의 CLI는 무엇인가요?

CLI는 **Command Line Interface**의 약자로 글자로 명령을 입력하는 방식입니다. GUI는 화면의 버튼·메뉴로 조작하는 방식입니다.

- `redis-server`: Redis 서버를 실행하는 프로그램
- `redis-cli`: 터미널에서 그 서버에 명령하는 프로그램
- Python의 `redis` 패키지: Python 코드에서 그 서버에 명령하는 클라이언트

`pip`로 설치한 Redis 패키지는 클라이언트입니다. 서버 실행과는 별개입니다.

## 6. 컨테이너 접속과 Redis CLI 접속은 어떻게 다른가요?

```bash
docker exec -it kdt-redis sh
```

컨테이너 안에서 **셸**을 엽니다. 셸은 입력한 명령을 해석하고 실행하는 프로그램입니다. `-i`는 입력을 열어 두고, `-t`는 터미널을 할당하고, `sh`는 실행할 셸 이름입니다.

컨테이너 셸에서는 `ls`, `redis-cli PING` 등을 실행할 수 있습니다.

```bash
docker exec -it kdt-redis redis-cli
```

이 명령은 셸 대신 **Redis 명령 입력 화면**을 바로 엽니다. 그 안에서는 `SET`, `GET`, `TTL` 등을 입력합니다.

`docker exec kdt-redis redis-cli`에서 대화형 입력을 하려는 경우 `-it`를 붙이는 것이 적절합니다. 반대로 `redis-cli PING`처럼 명령 하나를 전달하고 끝낼 때는 `-it`가 필요하지 않습니다.

```text
exit
```

셸이나 Redis CLI에서 나오는 명령입니다. Redis 서버를 종료하지 않습니다. 셸 안에서 CLI를 열었다면 CLI 종료 후 셸도 종료해야 Mac으로 돌아옵니다.

## 7. 컨테이너 상태·중지·시작·삭제 명령은?

| 명령 | 역할 |
|---|---|
| `docker ps` | 실행 중인 컨테이너만 표시 |
| `docker ps -a` | 중지된 것을 포함해 전체 표시. `a`는 all |
| `docker ps -al` | 가장 최근에 생성된 컨테이너 하나. 전체 조회와 다름 |
| `docker stop kdt-redis` | 중지. 컨테이너 자체는 남음 |
| `docker start kdt-redis` | 중지된 기존 컨테이너 실행 |
| `docker restart kdt-redis` | 중지 후 다시 실행 |
| `docker rm kdt-redis` | 중지된 컨테이너 삭제 |

삭제하려면 먼저 `stop`을 실행한 다음 `rm`을 사용합니다. `run`은 새로 만드는 명령, `start`는 기존 것을 다시 켜는 명령입니다. 컨테이너를 삭제해도 이미지는 별도로 남습니다.

`ps` 출력의 `NAMES`는 이름, `IMAGE`는 사용한 이미지, `STATUS`의 `Up`은 실행 중·`Exited`는 종료 상태, `PORTS`는 포트 연결입니다.

## 8. SET·GET·TTL은 무엇인가요?

Redis CLI에서:

```redis
SET day14:cli:message hello
GET day14:cli:message
TTL day14:cli:message
```

`SET 키 값`은 저장하며 같은 키가 있으면 덮어씁니다. `GET 키`는 값을 읽습니다. `day14:cli:message` 전체가 하나의 키이며 `:`가 폴더를 만들지는 않습니다.

Mac 터미널에서 바로 요청하려면:

```bash
docker exec kdt-redis redis-cli SET day14:cli:message hello
docker exec kdt-redis redis-cli GET day14:cli:message
docker exec kdt-redis redis-cli TTL day14:cli:message
```

TTL은 Time To Live, 남은 유효기간입니다.

| 반환값 | 뜻 |
|---|---|
| 0 이상 | 남은 시간(초) |
| `-1` | 키는 있지만 유효기간 없음 |
| `-2` | 키가 없음. 이미 만료된 경우 포함 |

```redis
EXPIRE day14:cli:message 60
SET practice:code 123456 EX 180
```

첫 줄은 기존 키에 60초 만료, 둘째는 저장과 동시에 180초 만료를 지정합니다. 자세한 의미는 [Redis TTL](https://redis.io/docs/latest/commands/ttl/)과 [SET](https://redis.io/docs/latest/commands/set/) 문서에서 확인할 수 있습니다. Docker 명령은 `bash`, Redis 명령은 `redis` 코드 블록으로 표시하면 구분하기 쉽습니다. SQL 명령과는 다릅니다.

## 9. uuid는 무엇인가요?

Python 기본 모듈로, 고유 식별자를 만들 때 사용합니다. 별도 pip 설치는 필요 없습니다.

```python
import uuid

id_text = str(uuid.uuid4())
key = f"day14:message:{uuid.uuid4().hex}"
```

`uuid4()`는 무작위 UUID 객체를 만들고 `str()`은 문자열로 변환합니다. `.hex`는 하이픈 없는 32자리 16진수 문자열 속성입니다. 같은 값이 나올 확률이 매우 낮아 실행마다 키 이름을 구분하기 좋습니다.

세션 ID에는 `secrets.token_urlsafe(32)`처럼 추측하기 어려운 토큰 생성 기능을 사용합니다. 여기서 32는 난수 바이트 수이며 결과 문자열의 글자 수가 아닙니다.

## 10. main.py의 저장·만료·삭제 코드는 어떤 흐름인가요?

질문에 제시한 코드는 다음 실험을 순서대로 실행합니다.

```text
모듈 가져오기 → .env 설정 읽기 → Redis 주소·포트 준비
→ UUID로 키 만들기 → Redis 클라이언트 준비 → PING
→ 만료 없이 저장 → 2초 만료로 덮어쓰기 → 3초 대기
→ 자동 만료 확인 → 다시 저장 → 직접 삭제
```

| 코드 | 해석 |
|---|---|
| `load_dotenv()` | `.env` 설정을 환경변수로 불러오기 |
| `os.getenv("REDIS_HOST")` | 서버 주소 읽기 |
| `int(port_text)` | 문자열 포트를 정수로 변환 |
| `with redis.Redis(...) as client:` | 클라이언트를 사용하고 종료 시 연결 자원 정리 |
| `client.ping()` | 정상 응답 시 Python의 `True` |
| `client.set(key, "Redis 연결 성공")` | 만료 없이 저장 |
| `client.get(key)` | 저장된 문자열 조회 |
| `client.set(key, "잠시 보관할 메시지", ex=2)` | 같은 키 덮어쓰기, 2초 만료 |
| `time.sleep(3)` | Python 프로그램 3초 대기 |
| `client.delete(key)` | 키 삭제, 실제 삭제 개수 반환 |

정상 흐름에서 TTL은 처음 `-1`, 두 번째 저장 직후 약 2초, 대기 후 `-2`입니다. 만료 후 `get()`은 `None`입니다. 마지막 `ex=30`은 삭제 코드 전에 프로그램이 끝나더라도 키가 무기한 남지 않게 합니다.

연결 옵션의 의미도 구분합니다.

- `decode_responses=True`: 문자열 응답을 `bytes` 대신 `str`로 반환. 모든 응답을 문자열로 바꾸지는 않음
- `socket_connect_timeout=2`: 연결 단계 제한 2초
- `socket_timeout=2`: 소켓 읽기·쓰기 단계 제한 2초. 프로그램 전체 실행 제한은 아님

클라이언트 객체 준비가 곧 연결 성공은 아닙니다. 보통 첫 Redis 명령에서 실제 연결합니다. `with` 종료는 클라이언트 정리이고 Redis 서버 종료가 아닙니다.

## 11. main3.py의 세션 코드는 무엇을 하나요?

**가상 사용자에게 60초짜리 입장권을 발급하고, 입장권으로 사용자를 확인하고, 입장권을 폐기하는 실습**입니다. 실제 비밀번호 인증은 없습니다.

```python
DEMO_USERS = {"demo-a": "민수", "demo-b": "지연"}
SESSION_TTL = 60
```

### 입력을 분석하는 단계

```python
parser.add_argument("command", choices=["create", "get", "logout"])
parser.add_argument("value")
args = parser.parse_args()
```

`python day14/main3.py create demo-a`를 실행하면 `args.command`는 `create`, `args.value`는 `demo-a`입니다. `command`는 할 일, `value`는 그 일에 사용할 값입니다.

### 설정과 연결 단계

환경변수에서 Redis 주소·포트를 읽고 필수값·정수·포트 범위를 확인한 뒤 클라이언트를 준비합니다. `Path(__file__).resolve().parent.parent / ".env"`는 파일 위치를 기준으로 프로젝트 루트의 `.env` 경로를 만드는 표현입니다. 질문 당시 명시적 경로를 전달한 코드와, 현재 `load_dotenv()`를 쓰는 파일은 [02 설명](02_파일별설명.md)에 구분되어 있습니다.

### create: 세션 생성

```python
session_id = "sid_" + secrets.token_urlsafe(32)
key = f"lesson03:session:{session_id}"
client.set(key, args.value, ex=SESSION_TTL)
```

Redis에는 `세션 ID → demo-a` 관계를 저장합니다. `sid_`는 토큰이 `-`로 시작해 명령줄 옵션으로 오인되는 일을 피합니다. 조회해도 60초 만료시간은 연장하지 않습니다.

### get: 사용자 확인

```python
user_id = client.get(key)
```

조회할 때는 사용자 ID가 아닌 **발급된 세션 ID**를 입력합니다. Redis에서 사용자 ID를 찾고 `DEMO_USERS[user_id]`로 이름을 표시합니다. 없거나 만료된 세션은 거절합니다.

### logout: 서버 기록 삭제

```python
client.delete(key)
```

세션 키를 삭제하면 같은 ID로 다시 조회해도 확인할 수 없습니다. 프로그램을 매번 새로 실행해도 Redis가 세션 정보를 유지하는 동안 연결 고리가 되어 줍니다.

파일 끝의 `if __name__ == "__main__":`은 직접 실행할 때 `main()`을 시작하게 합니다. `except`는 검증·Redis 오류를 처리하고 `SystemExit(1)`은 실패 상태로 종료하는 문법입니다. 구체적인 오류 해결 절차는 이 문서에서 다루지 않습니다.

## 12. SQLite 경로와 초기화 코드는 어떤 역할인가요?

`SQLITE_PATH`는 SQLite 데이터베이스 **파일 경로를 담는 환경변수 이름**입니다. SQLite는 별도 서버 없이 파일에 데이터를 저장하는 DB입니다.

```python
db_path = os.getenv("SQLITE_PATH")
with closing(sqlite3.connect(db_path)) as conn:
    initialize(conn)
```

DB 파일이 없으면 `connect()`가 생성할 수 있고, 기존 파일이면 연결합니다. 상대 경로는 현재 작업 폴더 기준입니다. `closing()`은 블록을 나갈 때 실제 연결을 닫습니다.

`initialize(conn)`은 대화 테이블을 준비합니다.

| 열 | 뜻 |
|---|---|
| `id` | 메시지 식별 번호. 정수 기본키 자동 부여 |
| `owner` | 메시지가 속한 사용자 ID |
| `role` | `user` 또는 `assistant` |
| `content` | 메시지 내용 |

```sql
CREATE TABLE IF NOT EXISTS messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner TEXT NOT NULL,
    role TEXT NOT NULL CHECK(role IN ('user', 'assistant')),
    content TEXT NOT NULL
)
```

`IF NOT EXISTS`는 테이블이 없을 때 생성, `NOT NULL`은 NULL 금지, `CHECK`는 허용된 역할 제한입니다. `NOT NULL`만으로 빈 문자열까지 금지하지는 않습니다.

```python
count = conn.execute("SELECT COUNT(*) FROM messages").fetchone()[0]
```

행 수를 조회합니다. `fetchone()`은 한 행, `[0]`은 그 행의 첫 열을 꺼냅니다. 행이 0개일 때만 `executemany()`로 예제 질문·답변 네 행을 넣습니다. `init`은 기존 데이터를 지우는 명령이 아닙니다.

```python
with conn:
    conn.executemany(
        "INSERT INTO messages(owner, role, content) VALUES (?, ?, ?)",
        [("demo-a", "user", "내 이름은 민수")],
    )
```

`?`는 값을 별도로 전달하는 자리입니다. SQL 문자열에 사용자 입력을 직접 이어 붙이지 않습니다. 이 코드의 쓰기 트랜잭션에서 `with conn`은 정상 시 commit, 예외 시 rollback을 관리하지만 연결 종료는 하지 않습니다. 연결 종료는 `closing()`의 역할입니다. [Python sqlite3 문서](https://docs.python.org/3.13/library/sqlite3.html#how-to-use-the-connection-context-manager)를 참고하세요.

## 13. day14 코드 전체는 무엇을 만들기 위한 것인가요?

**사용자를 구분하고, 대화를 기억하며, 원본과 캐시를 나눠 관리하는 터미널 대화 프로그램의 기초**를 쌓습니다.

| 파일 | 배우는 기능 | 서비스에 연결하면 |
|---|---|---|
| `main.py` | 저장·조회·만료·삭제 | 임시 정보 관리 |
| `main2.py` | String·Hash 조작 | 상태·프로필 관리 |
| `main2_teacher.py` | String·Hash·List 비교 | 자료에 맞는 저장 구조 선택 |
| `main3.py` | 세션 | 사용자 확인 |
| `main4.py` | 세션별 최근 대화 | 이전 질문을 참고한 응답 |
| `main5.py` | SQLite 원본과 Redis 캐시 | 조회 결과 재사용 |
| `main6.py` | 원본 추가와 버전별 캐시 | 오래된 결과 구분 |
| `main7.py` | 장애 대체 정책 | 캐시 대체와 사용자 확인 거절 비교 |
| `main8.py` | 기능 통합 | 사용자별 대화 프로그램 |

`main4.py`와 `main8.py`의 응답은 실제 AI 호출이 아닌 규칙 기반 모의 응답입니다. 각 파일은 독립 실행하며 키 접두사가 달라 한 파일의 세션을 다른 파일에서 사용할 수 없습니다.

## 15. Redis는 언제 사용하면 좋은가요?

자주 읽는 결과를 여러 프로그램이 공유하거나, 유효기간이 있는 정보를 관리하거나, 공통 카운터·순위가 필요할 때 유용합니다.

예를 들어 같은 인기 공고를 1,000명이 조회한다면 매번 외부 API에서 읽는 대신 잠시 보관한 결과를 재사용할 수 있습니다. 인증번호는 3분 뒤 만료시키고, 세션은 여러 서버에서 같은 기록을 조회할 수 있습니다.

항상 필요한 것은 아닙니다. 작은 서비스는 DB나 단일 프로세스 메모리로 시작할 수 있습니다. Redis를 추가하면 운영할 서버와 통신 비용도 생깁니다.

## 16. 카카오톡이나 네이버 쇼핑에서도 활용할 수 있나요?

아래는 친숙한 서비스를 빌린 **설계 예시**이며 해당 회사의 실제 제품 사용을 확인한 내용은 아닙니다.

| 서비스 상황 | Redis가 맡을 수 있는 일 | 다른 저장소의 역할 |
|---|---|---|
| 메신저 접속 상태 | 주기적으로 갱신하는 임시 상태 | 필요에 따른 사용자 원본 정보 |
| 최근 대화 조회 | 최근 대화 캐시 | 전체 대화 원본 보관 |
| 쇼핑 로그인 | 세션 공유 | 회원 계정 보관 |
| 인기 상품 조회 | 반복 조회 결과 캐시 | 상품 원본·변경 정보 보관 |
| 주문·결제 | 필요에 따른 보조 처리 | 정확한 거래 기록·재고 처리 |

상품 가격·재고가 바뀌면 캐시도 갱신해야 합니다. 결제 때는 최신 상태를 확인하는 정확한 처리 절차가 필요합니다. 사용자 앱은 보통 Redis에 직접 명령하지 않고 서비스 서버를 통해 기능을 사용합니다.

## 17. 채용 사이트의 모든 페이지에 Redis가 필요한가요?

필수가 아닙니다. 페이지보다 **어떤 정보를 얼마나 오래 보관할 것인지**를 기준으로 선택합니다.

| 기능 | Redis 없이도 가능한 구현 | 추가로 캐시한다면 |
|---|---|---|
| 로그인 | DB 세션·서명된 쿠키 등 | Redis에 세션 저장 |
| 채용 검색 | DB·검색 서비스 조회 | 자주 쓰는 검색 결과 |
| 적합도 분석 | 외부 모델 호출, 결과 보관 정책 선택 | 동일 조건의 분석 결과 |
| 저장한 채용공고 | 사용자 ID+공고 ID를 DB에 저장 | 목록 조회 결과 |
| 훈련 추천 | 부족 역량과 훈련 정보 비교 | 동일 조건의 추천 결과 |

“계속 보관할 저장 목록”과 “잠시 다시 쓸 조회 결과”는 수명이 다릅니다. Redis 사용 여부와 별도로 사용자별 접근 권한을 확인해야 합니다.

## 18. 다른 페이지로 이동해도 나라는 것을 어떻게 기억하나요?

브라우저가 쿠키 등의 사용자 확인 정보를 요청에 함께 보내고 서버가 검증합니다. 페이지마다 이름을 입력해 사용자라고 주장하는 방식이 아닙니다.

```text
로그인 → 세션 ID 발급 → 쿠키에 보관
검색 페이지 → 쿠키 전송 → 서버가 사용자 확인
저장 목록 페이지 → 쿠키 전송 → 같은 사용자 확인
```

서버 저장 세션에서는 `세션 ID → 사용자 ID` 관계를 DB나 Redis에 보관할 수 있습니다. 서명된 쿠키 세션에서는 작은 세션 내용 자체를 쿠키에 담을 수도 있습니다. **세션은 사용자 상태를 관리하는 방식이지 Redis라는 특정 제품의 이름이 아닙니다.**

## 19. Redis 없이 FastAPI에서 세션을 만들 수 있나요?

가능합니다. Starlette의 `SessionMiddleware`는 서명된 쿠키 기반 세션을 제공합니다. FastAPI에서 미들웨어로 추가할 수 있습니다. [FastAPI 미들웨어](https://fastapi.tiangolo.com/advanced/middleware/), [Starlette 세션](https://www.starlette.io/middleware/#sessionmiddleware)을 참고하세요.

핵심 코드 조각은 다음과 같습니다.

```python
app.add_middleware(
    SessionMiddleware,
    secret_key=환경에서_읽은_비밀키,
    max_age=1800,
    same_site="lax",
    https_only=False,  # 로컬 HTTP 실습용. HTTPS 운영에서는 True
)

# 계정 검증 성공 후
request.session["user_id"] = "demo-a"

# 다른 페이지 요청에서
user_id = request.session.get("user_id")

# 로그아웃
request.session.clear()
```

이 방식은 Redis에 저장하지 않고 쿠키에 내용을 담습니다. 서명은 변경·위조를 검출하는 장치이며 암호화가 아니므로 내용은 읽을 수 있습니다. 비밀번호나 민감한 개인정보는 넣지 않습니다.

공통 사용자 확인 함수를 만들어 `Depends(require_user)`로 보호할 API에 연결하면 페이지마다 검증 코드를 반복하지 않아도 됩니다. 전체 핵심 예제는 [05 서비스 활용](05_질문으로이해하는서비스활용.md)에 있습니다.

## 20. 외부 모델로 계산한 적합도를 재조회할 때 비용을 줄일 수 있나요?

같은 조건의 결과가 있으면 외부 모델을 호출하지 않고 반환하면 됩니다. FastAPI가 요청을 처리하고, 결과를 어디에 보관할지는 별도로 정합니다.

```text
세션으로 사용자 확인
    ↓
같은 조건의 결과가 있나?
    ├─ 있음 → 재사용
    └─ 없음 → 모델 호출 → 저장 → 반환
```

재사용 기준에는 다음을 포함할 수 있습니다.

```text
사용자 ID + 공고 ID + 프로필 버전 + 공고 버전 + 분석 방식 버전
```

이력서·공고·모델·프롬프트가 바뀌면 결과도 달라질 수 있기 때문입니다. 요청이 동시에 들어오면 같은 분석을 여러 번 호출할 수 있어 분석 중 상태·중복 방지도 별도로 필요합니다.

## 21. DB에 저장하지 않고 세션에 결과를 넣을 수 있나요?

가능합니다. 다만 **세션을 보관하는 장소**를 구분해야 합니다.

### 쿠키 세션

```python
request.session["analysis"] = {
    "job_id": 100,
    "profile_version": 3,
    "score": 85,
    "summary": "SQL 보완 권장",
}
result = request.session.get("analysis")
```

작은 실습 결과를 보관할 수 있습니다. 실제 재사용 전 공고·프로필·분석 버전 등을 함께 검사해야 합니다. 쿠키는 통상 약 4KB 수준의 제한이 있고 서명·인코딩도 공간을 쓰므로 긴 분석 보고서나 여러 결과에 적합하지 않습니다. 요청마다 전송되고 사용자도 내용을 읽을 수 있습니다. 로그아웃·만료·삭제 시 결과를 잃습니다.

### 서버 메모리 세션

브라우저에는 세션 ID만 두고 Python 메모리에 결과를 보관할 수도 있습니다. DB·Redis 없이 가능하지만 서버 재시작 시 사라지고, 여러 프로세스·서버가 자동 공유하지 못합니다. 만료·용량 정리도 직접 구현해야 합니다.

| 원하는 것 | 선택 예 |
|---|---|
| 로그인 중 작은 결과 잠깐 재사용 | 쿠키 세션 |
| 단일 프로세스 실습에서 큰 결과 잠깐 보관 | 서버 메모리 |
| 여러 서버가 임시 결과 공유 | Redis 같은 공유 캐시 |
| 다음 로그인·서버 재시작 후에도 보관 | DB |

쿠키 세션의 `clear()`는 현재 브라우저의 쿠키를 지우는 처리입니다. 이미 복사된 쿠키까지 즉시 서버에서 무효화하려면 별도 서버 기록 등의 설계가 필요합니다.

## 22. Redis는 로컬 서버에 있는 건가요?

실행 위치에 따라 다릅니다. 지금은 **내 Mac의 Docker 컨테이너**에 있고, 실제 서비스에서는 서비스 서버나 별도 클라우드 Redis에 둘 수 있습니다.

```text
실습: 내 Mac의 Python → 내 Mac Docker의 Redis
운영 예: 사용자 브라우저 → FastAPI 서버 → Redis 서버
```

Redis에 저장한 결과는 Redis 서버의 메모리에 있습니다. 브라우저 쿠키 세션의 결과는 사용자 브라우저에 있습니다. 둘은 보관 장소부터 다릅니다.

Python도 컨테이너에서 실행하면 그 컨테이너의 `127.0.0.1`은 그 컨테이너 자신입니다. 항상 Mac을 뜻하는 주소는 아닙니다.

## 23. 큰 서비스는 DB·Redis를 함께 쓰고 데이터센터에 저장하나요?

여러 역할의 저장소를 함께 사용하는 구조로 이해할 수 있습니다. 특정 회사의 실제 제품 채택은 공식 기술 자료로 별도 확인해야 합니다.

```text
사용자 기기
   ↓ 인터넷
서비스 인프라
   ├─ 애플리케이션 서버: 요청 처리
   ├─ DB: 보관할 회원·거래·분석 원본
   ├─ Redis: 세션·캐시·임시 정보
   └─ 파일 저장소: 사진·영상·이력서 파일
```

데이터센터는 전원·냉각·네트워크를 갖추고 컴퓨터를 운영하는 시설입니다. 클라우드 서비스 아래에도 실제 데이터센터의 장비가 있습니다. DB 파일은 주로 SSD 같은 저장장치에, Redis 데이터는 주로 RAM에 있고 설정에 따라 디스크에도 기록합니다.

한 컴퓨터에 여러 역할을 함께 두거나 여러 서버에 나눌 수 있고, 복제본을 두기도 합니다. 모든 정보가 한 서버에만 있는 것은 아니고 휴대폰·브라우저에도 쿠키나 최근 데이터가 저장될 수 있습니다.

## 24. 세션과 캐시는 어떻게 다른가요?

**세션은 사용자와 그 사용자의 상태를 유지하고, 캐시는 반복 조회·계산을 줄이기 위해 결과를 재사용합니다.** 둘은 저장 장소가 아니라 목적이 다릅니다.

| 구분 | 세션(Session) | 캐시(Cache) |
|---|---|---|
| 핵심 질문 | “누가 사용하는가? 어떤 상태인가?” | “이미 구한 결과를 다시 쓸 수 있는가?” |
| 채용 사이트 예시 | 이 요청의 사용자는 민수 | 민수와 공고 100번의 적합도는 85% |
| 없어지면 | 로그인 세션이라면 재로그인이 필요할 수 있음 | 원본을 조회하거나 다시 분석 |
| 보관 장소 | 쿠키·서버 메모리·DB·Redis 등 | 서버 메모리·Redis·DB 등 |
| 만료의 의미 | 기존 사용자 상태를 더 이상 유효하게 인정하지 않음 | 기존 사본을 재사용하지 않고 다시 조회·계산 |

세션이 항상 로그인만을 뜻하지는 않습니다. 로그인 전 사용자의 임시 상태도 관리할 수 있습니다. 이 수업의 세션은 주로 사용자 확인 용도입니다.

### 채용 적합도 조회 예시

```text
① 세션 확인
   “누가 요청했지?” → 민수

② 캐시 확인
   “민수의 현재 프로필과 현재 공고 조건으로 분석한 결과가 있나?”
      ├─ 있음 → 기존 결과 반환
      └─ 없음 → 외부 모델로 분석 → 결과 캐시 → 반환
```

세션이 유효해도 분석 캐시는 없을 수 있고, 세션이 만료되어도 서버의 분석 캐시는 남아 있을 수 있습니다. 두 정보의 만료시간은 독립적으로 정할 수 있습니다. 다시 로그인했을 때 같은 조건의 캐시가 남아 있다면 정책에 따라 재사용할 수 있습니다.

### 세션 안에 캐시를 넣을 수도 있나요?

가능합니다. 세션에 분석 결과를 저장하고 재조회에 사용하면 **세션에 담은 데이터를 캐시 용도로 활용**하는 것입니다.

```python
# SessionMiddleware가 준비한 쿠키 세션을 사용하는 예
request.session["user_id"] = "demo-a"  # 사용자 확인용 정보
request.session["analysis"] = {        # 재사용할 작은 결과
    "job_id": 100,
    "profile_version": 3,
    "job_version": 2,
    "analysis_version": 1,
    "score": 85,
}
```

재사용 전에는 공고·프로필·분석 버전이 현재 요청과 일치하는지 검사해야 합니다. `request.session.clear()`로 전체 세션을 비우면 사용자 ID와 분석 결과가 함께 지워집니다. 쿠키 세션이면 용량과 내용 노출 제약도 그대로 적용됩니다.

반대로 세션과 캐시를 별도 키로 관리한다면 로그아웃할 때 세션만 지우고 캐시는 남길 수 있습니다. day14의 `main8.py`가 이런 예입니다. 세션 키는 로그인 상태 확인에, 사용자별 캐시 키는 대화 조회 결과 재사용에 쓰며, 로그아웃은 세션 키만 삭제합니다. 다만 대화 원본은 SQLite가 보관하고 대화 캐시는 TTL에 따라 따로 만료됩니다.

| 생활 속 비유 | 역할 |
|---|---|
| 세션 = 입장권과 이용 상태 | 이 사람이 누구이고 서비스를 이용할 수 있는지 확인 |
| 캐시 = 미리 계산해 둔 결과 메모 | 같은 일을 다시 하지 않도록 결과 재사용 |

# 개념과 도구: 무엇이고, 왜 쓰고, 어떻게 활용할까?

## 1. 서버와 클라이언트

**서버**는 요청을 받아 일을 처리하는 프로그램, **클라이언트**는 요청을 보내는 프로그램입니다. 서버가 꼭 별도의 큰 컴퓨터를 뜻하는 것은 아닙니다.

음식점에서 주문을 받는 주방이 서버라면 주문하는 손님이 클라이언트입니다. 이 수업에서는 다음처럼 연결합니다.

```text
Mac의 Python 코드 ── redis 패키지로 요청 ──→ Docker 안의 Redis 서버
```

`redis-server`는 Redis 서버를 실행하는 프로그램입니다. `redis-cli`는 터미널에서 Redis에 요청하는 클라이언트이고, Python의 `redis` 패키지는 코드에서 요청하는 클라이언트입니다. **`pip install redis`만으로 Redis 서버가 실행되지는 않습니다.**

## 2. Redis: 여러 프로그램이 공유하는 빠른 저장소

Redis는 데이터를 주로 메모리(RAM)에 두고 빠르게 읽고 쓰는 저장소입니다. Python 딕셔너리처럼 키로 값을 찾되, 별도의 서버이므로 서로 다른 프로그램 실행에서도 공유할 수 있습니다.

```text
키                          값
lesson03:session:sid_abc     demo-a
product:10:name             노트북
```

키는 물건에 붙인 이름표, 값은 물건이라고 생각하면 됩니다. `:`는 이름 구분 관례이며 폴더를 만들지 않습니다.

왜 쓸까요? 자주 읽는 조회 결과를 빠르게 제공하거나, 여러 앱 서버가 같은 로그인 상태를 확인하거나, 유효기간이 있는 인증 정보를 관리하기 좋습니다. 단, 로컬의 작은 SQLite 조회에서는 Redis 통신과 변환 비용 때문에 반드시 더 빨라지는 것은 아닙니다. 이 수업은 처리 속도 비교보다 구조를 배우는 실습입니다.

Python 사용 예:

```python
with redis.Redis(host="127.0.0.1", port=6379, decode_responses=True) as client:
    client.set("practice:message", "안녕하세요", ex=60)
    print(client.get("practice:message"))
```

`set`으로 저장하고 `get`으로 읽습니다. `ex=60`은 60초 후 만료입니다. 기본 연결 방식은 [Redis Python 연결 안내](https://redis.io/docs/latest/develop/clients/redis-py/connect/)에서도 확인할 수 있습니다.

## 3. Docker·이미지·컨테이너

Docker는 프로그램과 실행 환경을 묶은 **이미지**를 이용해 **컨테이너**라는 분리된 실행 공간에서 프로그램을 실행하는 도구입니다.

| 개념 | 정의 | 이 수업의 예 |
|---|---|---|
| Docker | 컨테이너 생성·실행·관리를 돕는 도구 | Mac의 Docker Desktop |
| 이미지 | 프로그램과 필요한 파일을 담은 실행 패키지 | `redis:7.4` |
| 컨테이너 | 이미지로 생성한 실행 공간 | `kdt-redis` |
| Dockerfile | 이미지를 만드는 방법을 적은 파일 | 이 수업은 공식 이미지를 쓰므로 필요 없음 |

이미지가 조리법과 재료를 담은 밀키트라면, 컨테이너는 실제 요리할 작업 공간입니다. 하나의 이미지로 여러 컨테이너를 만들 수 있습니다.

왜 쓰나요? Redis를 직접 설치하고 버전을 관리하는 과정을 줄이고, 다른 사람도 비슷한 환경으로 실습할 수 있기 때문입니다. Python 코드는 Mac에서 실행하고 Redis만 Docker에서 실행합니다. Python까지 자동으로 컨테이너에 들어가는 것은 아닙니다.

```bash
docker run -d --name kdt-redis -p 127.0.0.1:6379:6379 redis:7.4 redis-server --save "" --appendonly no
```

이미지를 로컬에서 찾고, 없으면 내려받아 새 컨테이너를 만듭니다. 명령 전체 해석은 [실행 안내](04_실행과오류해결.md)에 있습니다.

## 4. 주소와 포트: 어느 건물의 어느 창구인가?

`127.0.0.1`은 **현재 프로그램이 실행되는 컴퓨터 자신**을 가리킵니다. 포트는 그 컴퓨터에서 어떤 서비스로 연결할지 정하는 번호입니다. 주소가 건물 주소라면 포트는 창구 번호입니다.

```text
Mac Python → 127.0.0.1:6379 → Docker의 연결 통로 → Redis 컨테이너:6379
```

`-p 127.0.0.1:6379:6379`는 `Mac에서 사용할 주소:Mac 포트:컨테이너 포트` 순서입니다. 이 실습은 Mac 내부 접속용으로 공개합니다. [Docker 포트 연결 설명](https://docs.docker.com/get-started/docker-concepts/running-containers/publishing-ports/), [localhost 바인딩 설명](https://docs.docker.com/engine/network/port-publishing)을 참고하세요.

Python도 별도 컨테이너에서 실행한다면 그 안의 `127.0.0.1`은 해당 컨테이너 자신이므로, 지금 설정을 그대로 적용할 수 없습니다.

## 5. TTL: 데이터의 유효기간

TTL(Time To Live)은 키가 만료되기까지 남은 시간입니다. 우유의 소비기한처럼 “언제까지 쓸 수 있는가”를 지정합니다.

```python
client.set("practice:code", "123456", ex=180)
print(client.ttl("practice:code"))
```

인증번호를 3분 뒤 못 쓰게 하거나, 오래된 캐시를 자동으로 정리할 때 사용합니다.

| `ttl()` 결과 | 뜻 |
|---|---|
| 0 이상의 정수 | 남은 초. `0`이면 만료 직전일 수 있음 |
| `-1` | 키는 있고 만료시간은 없음 |
| `-2` | 키가 없음 |

키가 만료되면 `get()`은 `None`을 반환합니다. TTL이 없더라도 Redis가 종료되면 데이터가 보존된다는 뜻은 아닙니다. 이 수업의 Docker 명령은 RDB 자동 저장과 AOF 기록을 끄므로 Redis를 중지하고 다시 시작하면 실습 데이터가 사라집니다. Redis 자체에는 별도의 영속화 기능도 있습니다.

## 6. String·Hash·List: 용도에 따라 다른 그릇

| 자료형 | 개념과 비유 | 활용 예 | 주요 함수 |
|---|---|---|---|
| String | 이름표 하나에 값 하나 | 상태, 세션의 사용자 ID, JSON 캐시 | `set`, `get` |
| Hash | 카드 한 장에 여러 항목 | 이름·등급이 있는 프로필 | `hset`, `hget`, `hgetall` |
| List | 순서가 있는 메모 묶음 | 질문·답변 순서 유지 | `rpush`, `lrange`, `ltrim` |

```python
client.hset("practice:profile", mapping={"name": "민수", "level": "basic"})
client.rpush("practice:messages", "첫 질문", "첫 답변")
```

Hash를 `get()`으로 읽으면 자료형 오류가 납니다. `hgetall()`처럼 그릇에 맞는 명령을 사용해야 합니다. `main4.py`는 메시지별 JSON을 Redis List에 저장하고, `main5.py` 이후는 메시지 목록 전체를 JSON 문자열로 만들어 Redis String에 저장합니다.

## 7. 세션: 서버가 기억하는 임시 사용자 확인 정보

세션은 어떤 요청을 어떤 사용자의 것으로 처리할지 서버가 기억하는 정보입니다. 여기서는 **추측하기 어려운 세션 ID → 사용자 ID** 관계를 Redis에 저장합니다.

```text
sid_난수문자열 → demo-a → 민수
```

놀이공원 입장권 번호로 입장 자격을 확인하는 것과 비슷합니다. 다음 요청에 세션 ID를 제출하면 서버가 Redis에서 실제 사용자 ID를 찾습니다.

```python
session_id = "sid_" + secrets.token_urlsafe(32)
client.set(f"lesson03:session:{session_id}", "demo-a", ex=60)
```

이점은 사용자 정보를 요청마다 직접 믿지 않고 서버의 기록으로 확인할 수 있고, 키를 삭제해 로그아웃시킬 수 있다는 것입니다. 실제 서비스에서는 비밀번호 등의 인증 후 발급하지만 이 실습은 가상 사용자 선택만 구현합니다. 세션 ID는 사용자의 이름이나 비밀번호를 암호화한 값이 아닙니다.

## 8. 대화 이력과 문맥: 답변에 필요한 이전 메모

**대화 이력**은 저장된 질문과 답변이고, **문맥**은 이번 응답을 만들 때 참고하는 정보입니다.

```python
{"role": "user", "content": "내 이름은 민수"}
{"role": "assistant", "content": "모의 응답: 내 이름은 민수"}
```

`role`은 누가 말했는지, `content`는 내용입니다. 한 번의 질문과 답변을 한 **턴(turn)**이라고 부릅니다. `MAX_MESSAGES=6`은 여섯 질문이 아니라 정상적으로 저장된 질문·답변 **세 턴**입니다.

이전 대화를 전달하면 “내 이름이 뭐야?” 같은 질문에 연결해서 답할 수 있습니다. 이 수업에서는 `make_demo_reply()`가 이전 사용자 메시지에서 `내 이름은 `으로 시작하는 문장을 찾습니다. 실제 AI 추론이 아닙니다. 최근 6개 밖으로 밀려난 정보는 SQLite에 남아 있어도 이번 응답 문맥에는 포함되지 않을 수 있습니다.

## 9. JSON: 데이터를 문자열로 포장하는 형식

JSON은 목록과 사전 같은 구조를 문자열로 표현하는 형식입니다. 택배 포장처럼 Python 데이터를 Redis에 보관하기 쉬운 형태로 바꿉니다.

```python
messages = [{"role": "user", "content": "안녕"}]
raw = json.dumps(messages, ensure_ascii=False)  # Python → JSON 문자열
restored = json.loads(raw)                      # JSON 문자열 → Python
```

JSON 변환은 암호화가 아닙니다. `decode_history()`는 복원된 내용이 올바른 목록·사전·문자열인지 확인해 잘못된 데이터를 거릅니다.

## 10. SQLite: 파일에 보관하는 원본 장부

SQLite는 별도의 DB 서버 없이 파일에 데이터를 저장하고 SQL로 조회하는 데이터베이스입니다. 이 수업에서는 `messages.db` 같은 파일이 원본 장부입니다. Python의 `sqlite3`는 기본 제공 모듈입니다.

| id | owner | role | content |
|---|---|---|---|
| 1 | demo-a | user | 내 이름은 민수 |
| 2 | demo-a | assistant | 모의 응답: 내 이름은 민수 |

프로그램이나 Redis를 종료해도 파일이 남으면 대화 원본을 다시 읽을 수 있습니다. 작은 로컬 앱, 학습용 앱에서 시작하기 편합니다. Redis와 SQLite는 이 수업에서 서로 다른 역할을 맡습니다.

## 11. 캐시와 HIT·MISS: 원본을 빨리 꺼내기 위한 사본

캐시는 **다시 만들 수 있는 조회 결과를 잠시 보관한 사본**입니다. 장부를 읽어 정리한 결과를 책상 위에 놓는 것과 같습니다.

```text
조회 요청 → Redis에 있나?
             ├─ 있음: HIT → 캐시 결과 사용
             └─ 없음: MISS → SQLite 조회 → Redis에 60초 저장 → 결과 사용
```

이 방식을 cache-aside라고 부릅니다. 애플리케이션이 캐시를 직접 확인하고 채웁니다. 많은 요청에서 동일한 목록을 반복 계산하거나 조회하는 부담을 줄일 수 있습니다.

빈 목록을 저장한 JSON `"[]"`도 유효한 캐시입니다. 조회 결과가 비어 있다는 사실도 기억할 가치가 있습니다. 그래서 `if raw is not None:`으로 키 유무를 검사합니다.

## 12. 캐시 무효화와 버전: 오래된 사본을 고르지 않기

원본에 새 대화를 저장했는데 예전 캐시를 읽으면 새 내용이 보이지 않습니다. 이를 막기 위해 원본 저장 후 이전 캐시를 삭제하는 것이 **캐시 무효화**입니다.

`main6.py` 이후는 최신 메시지 ID도 키에 붙입니다.

```text
추가 전: lesson06:history:demo-a:v4
추가 후: lesson06:history:demo-a:v6
```

질문·답변 두 행이 추가되면 최신 ID가 바뀌어 다음 조회가 새 키를 선택합니다. 삭제 실패로 예전 키가 남아도 새 버전 조회에는 사용하지 않습니다. 예전 키는 TTL로 정리됩니다. 실제 ID는 공유 DB의 이전 저장 내역에 따라 달라집니다.

HIT여도 현재 버전을 알기 위한 작은 SQL 조회는 실행합니다. 또한 이 방식은 **새 메시지를 추가하는 실습**에 맞춘 것입니다. 기존 행의 내용만 수정하면 `MAX(id)`가 안 바뀌므로, 모든 수정·삭제·동시 실행의 일관성을 해결하는 방식은 아닙니다.

## 13. 트랜잭션과 장애 대체

트랜잭션은 여러 쓰기를 한 묶음으로 확정하거나 취소하는 단위입니다. 질문 저장만 성공하고 답변 저장은 실패하면 기록이 어긋나므로 `save_turn()`은 두 행을 함께 저장합니다.

- **commit**: 저장 확정
- **rollback**: 묶음의 변경 취소
- **fallback**: 원래 경로를 못 쓰면 대체 경로 사용

캐시가 고장 났을 때는 SQLite 원본으로 대체할 수 있습니다. 하지만 세션 확인이 불가능할 때 사용자를 추측해서 통과시킬 수는 없습니다. `main7.py`는 두 정책을 따로 보여주고 `main8.py`는 모든 대화 요청 앞에 세션 확인을 연결합니다.

# Supabase Auth 쇼핑몰: 로컬 실행과 피드백

대상 폴더는 `day12/shoppingmall`입니다. 로그인·비밀번호·이메일 인증은 Supabase Auth가 담당합니다. 이름·주소·쇼핑몰 이용 상태·역할은 `shoppingmall.users`가 담당하며 `auth_user_id`로 연결됩니다. 결제는 기존과 같이 모의 결제입니다. 배포는 하지 않았습니다.

## 1. 준비

프로젝트 최상위 `AIO_4_class`에서 실행합니다.

```bash
conda activate py313
cd day12/shoppingmall
python -m pip install -r requirements.txt
```

Supabase의 별도 개발용 프로젝트 사용을 권장합니다. 이 앱은 시작할 때 `schema.sql`을 실행해 컬럼·테이블·RLS 설정을 추가하고 예시 상품을 준비합니다. 기존 데이터를 삭제하지 않지만 **테이블 구조와 Data API 접근권한을 변경**하므로, 기존 DB는 먼저 백업하세요. DB 연결 계정은 테이블 소유자(일반적으로 Session pooler의 postgres 계정)여야 합니다. 이 버전의 shoppingmall 스키마는 브라우저 Data API 직접 접근을 차단합니다. 다른 앱에서 이 스키마를 직접 사용한다면 분리된 개발 DB에서 먼저 검증하세요.

`shoppingmall/.env`가 없으면 `.env.example`을 복사해 이 폴더에 `.env`를 만드세요. 프로젝트 최상위 `.env`도 탐색하지만, 쇼핑몰 전용 파일이 우선입니다. 실행 환경에 이미 있는 값은 파일보다 우선합니다.

```dotenv
# Supabase Connect → Session pooler. 위 Auth와 반드시 같은 프로젝트
host=YOUR_POOLER_HOST
port=5432
dbname=postgres
user=postgres.YOUR_PROJECT_REF
password=YOUR_DB_PASSWORD

# Project URL과 publishable API key. DB host/password와 다른 값입니다.
SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
SUPABASE_PUBLISHABLE_KEY=sb_publishable_YOUR_KEY

# 아래 명령으로 만든 키를 넣으세요. 예시 문자열 그대로 사용하면 실행되지 않습니다.
AUTH_SESSION_KEY=GENERATED_FERNET_KEY
COOKIE_SECURE=false
```

암호화 키 생성:

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

키는 `.env`에만 저장하고 Git에 올리지 마세요. 서버 재시작마다 새로 만들지 마세요. 키 변경 시 기존 세션은 복호화할 수 없어 다시 로그인해야 합니다. 여러 서버에서는 같은 키를 사용합니다. DB 백업과 암호화 키는 별도로 보관하세요.

Supabase Auth에서 이메일/비밀번호 가입을 활성화하고 Site URL에 `http://127.0.0.1:8000`을 설정하세요. 이메일 확인을 켰다면 실제 받을 수 있는 이메일로 가입하고 메일의 링크를 누른 뒤 쇼핑몰에서 로그인합니다. 이 버전은 확인 링크에 포함된 토큰을 브라우저 세션으로 가져오는 자동 로그인 대신 명시적인 재로그인을 사용합니다.

## 2. 실행

```bash
python -m uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

- 쇼핑몰: http://127.0.0.1:8000
- API 문서: http://127.0.0.1:8000/docs
- 상태 확인: http://127.0.0.1:8000/health (프로세스 응답 확인용)
- 종료: `Ctrl + C`
- `.env` 수정 후에는 서버를 완전히 종료하고 다시 실행하세요.

### Swagger에서 회원가입·로그인 테스트

1. 서버를 재시작하거나 `--reload`의 재시작 완료를 기다린 뒤 http://127.0.0.1:8000/docs 를 새로고침합니다.
2. `POST /api/signup` → **Try it out**을 누릅니다.
3. **Parameters → X-Shop-Request**의 기본값 `1`을 유지합니다. 이 값은 비밀번호나 토큰이 아닌 요청 보호용 표시입니다.
4. Request body에 이름·주소·이메일·비밀번호를 입력하고 **Execute**합니다.
5. 실제 이메일 확인까지 시험하려면 받을 수 있는 이메일 주소를 사용하세요.

POST/PUT/PATCH/DELETE 경로에는 필요한 헤더가 표시되며 Swagger가 함께 전송합니다. 누락되면 고객에게는 새로고침·홈 재접속 안내를 표시합니다. 응답의 `detail`과 `hint`는 고객용 문구이며, `code`는 개발자 진단용 식별값입니다. 다른 출처 요청은 계속 차단하며, `localhost`와 `127.0.0.1`을 섞지 말고 같은 호스트·포트를 사용하세요.

보호 API는 Bearer JWT를 직접 받지 않고 로그인 응답의 HttpOnly 세션 쿠키를 사용합니다. `/api/login`도 같은 문서에서 실행하면 브라우저가 받은 쿠키를 이후 요청에 보냅니다. curl/Postman을 쓴다면 `X-Shop-Request: 1`을 직접 추가하세요.

## 3. 권한별 기능

| 기능 | 비회원 | 일반 회원 | 관리자 |
|---|---|---|---|
| 판매 중 상품 조회 | 가능 | 가능 | 가능 |
| 장바구니·모의 결제 | 로그인 필요 | 본인만 | 본인만 |
| 주문 상세·결제 정보 | 로그인 필요 | 본인만 | 고객용 API에서는 본인만 |
| 이름·배송지 수정·쇼핑몰 탈퇴 | 로그인 필요 | 본인만 | 본인만 |
| 판매 중지 상품 조회·상품 등록/수정 | 불가 | 불가 | 가능 |
| 전체 결제 주문 조회·배송 상태 변경 | 불가 | 불가 | 가능 |
| 관리자 승격 | 불가 | 불가 | 웹 API 미제공, 신뢰할 수 있는 DB 운영자만 |

관리자는 로그인한 DB 프로필의 `role`을 매 요청마다 확인합니다. 회원가입 JSON, 프로필 수정, Supabase `user_metadata`에 `role=admin`을 넣어도 권한을 얻을 수 없습니다. 사용자 ID를 요청으로 받아 본인으로 간주하지 않습니다. 장바구니·주문 소유권은 서버가 확인한 ID로 SQL에서 제한합니다.

가격·합계·재고는 서버에서 계산합니다. 판매 중지된 상품은 신규 담기와 결제가 불가능하며 과거 주문은 유지됩니다. 배송은 준비 → 배송 중 → 배송 완료 순서로만 이동합니다. 환불·실제 결제·택배 연동은 포함하지 않습니다.

## 4. 관리자 지정과 해제

먼저 테스트 계정으로 가입·이메일 확인·로그인해 프로필을 생성하세요. Supabase SQL Editor에서 Auth UUID와 프로필을 직접 확인한 후 다음을 실행합니다. 이메일 문자열이 아닌 **확인한 Auth UUID**를 사용하세요.

```sql
SELECT id, auth_user_id, email, role, active FROM shoppingmall.users;

UPDATE shoppingmall.users SET role = 'admin'
WHERE auth_user_id = '확인한-Auth-사용자-UUID'::uuid AND active;
```

쇼핑몰을 새로고침하면 관리자 메뉴가 보입니다. 상품의 가격·재고·판매 상태를 변경하고 주문 배송 상태를 관리할 수 있습니다. 권한 해제도 다음 요청부터 반영됩니다.

```sql
UPDATE shoppingmall.users SET role = 'customer'
WHERE auth_user_id = '확인한-Auth-사용자-UUID'::uuid;
```

## 5. 기존 회원 전환

기존 PBKDF2 비밀번호로 자동 로그인하지 않습니다. 기존 `users.id`, 주문·결제는 유지하고 이전 자체 `sessions`는 사용하지 않습니다. 비밀번호 해시는 현재 인증에 사용하지 않습니다.

기존 이메일과 새 Auth 이메일이 같아도 자동 연결하지 않습니다. 자동 연결하면 이메일의 소유권과 기존 계정의 소유권을 잘못 연결할 수 있기 때문입니다. 운영자가 기존 회원의 소유권을 별도 확인한 후, Supabase Auth에 등록하고 이메일 인증을 완료한 계정의 UUID를 연결하세요. 새 Auth 비밀번호를 사용합니다. Auth의 이메일 인증 여부만으로 기존 쇼핑몰 계정 소유권이 입증되는 것은 아닙니다.

```sql
-- 대상과 UUID를 둘 다 검토한 뒤 트랜잭션으로 진행
BEGIN;
UPDATE shoppingmall.users
SET auth_user_id = '확인한-Auth-사용자-UUID'::uuid,
    password_hash = ''
WHERE id = 검토한_기존회원_ID AND auth_user_id IS NULL AND active;
-- 영향받은 행이 정확히 1개인지 확인 후 COMMIT; 아니면 ROLLBACK;
COMMIT;
```

이후 최초 로그인부터 기존 회원 ID의 장바구니·주문을 그대로 사용합니다. 롤백 배포를 하려면 변경 전 코드와 DB 백업이 필요합니다. 새 비밀번호를 직접 DB에 저장하거나 Auth 비밀번호 해시를 복사하지 마세요.

## 6. 수동 검증: 서로 다른 두 계정으로 확인

일반 창의 회원 A, 시크릿 창의 회원 B를 사용하세요.

1. 비회원으로 상품 목록을 확인합니다. 장바구니·내 정보 진입 시 로그인을 요구해야 합니다.
2. A로 가입합니다. 이메일 확인을 켰다면 인증 전 로그인이 거절되고 인증 후 성공해야 합니다.
3. A로 담기·주소 변경·모의 결제를 수행합니다. 구매내역의 가격·수량·배송지가 맞는지 확인합니다.
4. B로 로그인합니다. A의 장바구니·주문이 보이지 않아야 합니다. A의 주문 번호로 `/api/orders/{id}`를 요청하면 404여야 합니다.
5. 일반 회원이 `/api/admin/products`, `/api/admin/orders`를 요청하면 403이어야 합니다.
6. A를 SQL로 관리자 지정하고 새로고침합니다. 관리자 메뉴에서 상품 등록·가격/재고 수정·판매 중지를 확인합니다.
7. 이미 담긴 상품을 관리자가 판매 중지한 다음 결제하면 거절되어야 합니다. 재고를 줄여도 부족하면 전체 결제가 취소되어야 합니다.
8. 결제 주문의 배송 상태를 순서대로 변경하고 고객 구매내역에 반영되는지 확인합니다. 뒤로 되돌리기는 거절되어야 합니다.
9. 관리자 권한을 SQL로 해제하면 이미 열려 있는 관리자 화면에서도 다음 API 요청이 거절되어야 합니다.
10. 로그아웃 후 뒤로가기·새로고침·보관한 쿠키 재사용으로 보호 API에 접근할 수 없어야 합니다. API 응답에는 `Cache-Control: no-store`가 있어야 합니다.
11. 쇼핑몰 탈퇴 후 기존 세션과 신규 로그인은 차단되고 주문 이력은 보존되어야 합니다. **탈퇴는 쇼핑몰 프로필 이용 중지·개인정보 익명화입니다. Supabase Auth 계정과 메타데이터 삭제는 운영자가 별도로 처리**해야 합니다. 다른 앱과 공유하는 Auth 계정을 임의 삭제하지 않기 위한 범위입니다.

이메일 확인 메일은 Supabase의 개발용 메일 제한에 영향을 받을 수 있습니다. 메일이 오지 않으면 Auth 대시보드와 메일 설정을 확인하세요.

## 7. curl로 API 확인

아래는 bash/zsh 예시입니다. `curl -b` 쿠키 파일에는 민감한 세션이 있으니 공유하지 마세요. 비밀번호를 터미널 기록에 직접 적지 않도록 입력 파일을 사용합니다.

```bash
# 테스트용 login.json을 로컬에 생성 (Git에 올리지 않기)
# 내용: {"email":"실제 테스트 이메일","password":"테스트 비밀번호"}
curl -i -c /tmp/soso-cookies.txt \
  -H 'Content-Type: application/json' -H 'X-Shop-Request: 1' \
  --data-binary @login.json http://127.0.0.1:8000/api/login

curl -i -b /tmp/soso-cookies.txt http://127.0.0.1:8000/api/me
curl -i -b /tmp/soso-cookies.txt http://127.0.0.1:8000/api/orders
curl -i -b /tmp/soso-cookies.txt http://127.0.0.1:8000/api/orders/주문번호
curl -i -b /tmp/soso-cookies.txt http://127.0.0.1:8000/api/admin/orders

curl -i -b /tmp/soso-cookies.txt -H 'X-Shop-Request: 1' \
  -X POST http://127.0.0.1:8000/api/logout

# 로그아웃 전 쿠키 파일을 그대로 재사용해도 401이어야 합니다.
curl -i -b /tmp/soso-cookies.txt http://127.0.0.1:8000/api/me
```

테스트 후 쿠키 파일과 `login.json`은 직접 삭제하세요. 역할·토큰·DB 비밀번호를 피드백에 붙이지 마세요.

## 8. 자동 검증

통합 테스트는 **실제 PostgreSQL + 모의 Supabase Auth**를 사용합니다. 실제 Auth 계정 생성·메일 발송·운영 DB 변경은 하지 않습니다. `anon`, `authenticated` 역할이 있는 로컬 PostgreSQL에 `_test`로 끝나는 전용 DB를 만드세요. 테스트가 그 DB의 쇼핑몰 데이터를 초기화하므로 운영 DB를 지정하면 안 됩니다. 같은 이름 규칙만으로 로컬 DB 여부를 보증하지는 않으니 호스트도 확인하세요.

```bash
python -m pip install -r requirements-dev.txt
# 로컬 PostgreSQL의 postgres 관리 계정에서 최초 1회
psql -h localhost -U postgres -c 'CREATE DATABASE shoppingmall_test;'
# 아래 두 역할은 없는 경우에만 생성
psql -h localhost -U postgres -c 'CREATE ROLE anon;'
psql -h localhost -U postgres -c 'CREATE ROLE authenticated;'

# 비밀번호를 DSN에 직접 적는 대신 로컬 .pgpass 사용 가능
export TEST_DATABASE_URL='host=localhost port=5432 dbname=shoppingmall_test user=postgres'
python -m pytest tests -q
```

환경변수가 없으면 DB 통합 테스트는 건너뜁니다. 따라서 skipped는 통과로 간주하지 마세요. 실제 Supabase의 이메일 발송·Auth 설정·실제 토큰 발급은 위 수동 검증으로 추가 확인해야 합니다.

## 9. 인증 설계와 운영 범위

- 브라우저는 HttpOnly / SameSite=Lax 쿠키의 무작위 세션 ID만 받습니다. JWT·refresh token을 JS/localStorage에 전달하지 않습니다.
- DB에는 세션 ID의 SHA-256 해시와 Fernet로 암호화한 Supabase 토큰을 저장합니다. 세션은 최대 7일이며 만료 임박한 access token은 refresh token으로 갱신합니다. 갱신은 DB 행 잠금으로 직렬화합니다.
- 보호 요청마다 Supabase `/user`에서 토큰을 검증하고 DB의 현재 역할·이용 상태를 확인합니다. Auth 서비스 장애 시 보호 기능은 503으로 거절합니다.
- 로그아웃은 로컬 세션을 먼저 삭제하고 Supabase의 현재 세션 해제를 요청합니다. Auth 통신 실패 시에도 앱 쿠키는 재사용 불가하며, 화면에 서버 세션 해제 미확인 문구를 표시합니다. 이미 발급된 JWT 자체는 만료 전까지 다른 서비스에서 유효할 수 있습니다.
- POST/PUT/PATCH/DELETE는 같은 출처 확인과 `X-Shop-Request: 1` 헤더가 필요합니다. 외부 출처 CORS를 열지 마세요.
- DB 직접 연결은 테이블 소유자이므로 이 앱의 권한 검사를 통과한 SQL만 실행합니다. 브라우저 Data API에는 RLS와 권한 회수로 별도 접근을 막습니다. 사용자별 RLS 쿼리로 전환하려면 별도의 설계가 필요합니다.
- 현재 상품·배송 상태는 관리자만 수정합니다. 별도 판매자/상담원, 관리자 MFA, 반품·환불, 비밀번호 재설정 UI, 감사로그는 후속 범위입니다.
- 공개 배포 전 `COOKIE_SECURE=true`, HTTPS, 적절한 Auth 메일 설정과 로그인/가입 속도 제한 등을 점검하세요. 이 문서는 로컬 테스트 절차이며 배포 실행은 포함하지 않습니다.

근거: [Supabase Auth 세션](https://supabase.com/docs/guides/auth/sessions), [Auth API](https://github.com/supabase/auth), [로그아웃과 JWT 만료](https://supabase.com/docs/reference/python/auth-signout).

## 10. 피드백 기록

테스트 후 다음 형식으로 알려주시면 해당 사례를 재현해 개선할 수 있습니다.

| 항목 | 작성 예시 |
|---|---|
| 계정 권한 | 비회원 / 일반 회원 A·B / 관리자 |
| 화면·동작 | 장바구니 → 모의 결제 |
| 기대한 결과 | 본인 구매내역에 주문 1건 표시 |
| 실제 결과 | 화면 메시지 또는 HTTP 상태 |
| 재현 순서 | 로그인 → 상품 담기 → 배송지 입력 → 결제 |
| 개선 희망 | 관리자에게 재고 부족 상품을 먼저 표시 |

비밀번호·쿠키·JWT·refresh token·DB 연결 문자열은 지우고 공유하세요. 현재 사용자 피드백은 아직 수집 전이며, 실제 의견을 받은 뒤 재현·수정·재검증합니다.

## 이번 작업의 검증 결과와 반영한 피드백

2026-10-30 로컬 검증:

- 임시 로컬 PostgreSQL 18 + 모의 Auth로 자동 테스트 **19개 통과**.
- Python 컴파일 검사, JavaScript 문법 검사, Git diff 공백 검사 통과.
- 일반 회원의 관리자 API 차단, 주문·결제 소유권 제한, 관리자 해제 반영, 토큰 암호화·동시 갱신, 로그아웃 쿠키 재사용 차단, Auth 장애 시 로컬 로그아웃, 탈퇴 차단, Data API 역할 접근 차단을 확인했습니다.
- 판매 중지 상품의 결제 차단과 서버 재시작 후 수정한 예시 상품의 중복 생성 방지도 확인했습니다.
- 테스트용 PostgreSQL은 종료했습니다. 실제 Supabase Auth 호출·메일 발송과 브라우저 화면에서의 전체 구매 흐름은 아직 검증하지 않았습니다. 실제 Supabase DB 마이그레이션과 배포도 실행하지 않았습니다.

받은 피드백: “어떻게 테스트해야 하나요?”

반영: 문서 첫 부분에 최소 실행 명령어와 화면 조작 순서를 추가하고, 현재 작업 폴더에 로컬 암호화 키를 준비했습니다. 실제 사용 후의 동작·화면 피드백은 추가로 받아 반영합니다.


### 고객 안내와 개발자 진단 구분

고객에게는 헤더·Swagger·JSON 같은 용어 대신 새로고침이나 쇼핑몰 홈 재접속을 안내합니다. 개발자는 아래 식별값으로 수정 위치를 확인하세요. 이 표는 개발 문서용이며 고객 화면에 표시하지 않습니다.

| 응답의 code | 개발자가 확인할 내용 |
|---|---|
| `SHOP_REQUEST_HEADER_REQUIRED` | 요청에 `X-Shop-Request: 1`이 포함되는지 확인. Swagger 문서를 새로고침하고 헤더 기본값 유지 |
| `CROSS_ORIGIN_REQUEST_BLOCKED` | 화면과 API의 출처가 같은지 확인. 호스트·포트 및 프록시 설정 점검 |


### 회원가입 화면의 실패 안내

회원가입 실패를 로그인 오류로 뭉뚱그리지 않고 Auth가 반환한 오류 종류에 따라 안내합니다. `error_code`와 `code` 두 응답 형식을 지원합니다.

| 원인 | 고객에게 안내할 내용 |
|---|---|
| 가입 불가 이메일 | 예시 주소 대신 실제 메일을 받을 수 있는 주소 입력 |
| 비밀번호 조건 미충족 | 더 긴 비밀번호와 문자 조합 사용 |
| 이미 가입된 이메일 | 로그인하거나 다른 이메일 사용 |
| 이메일 발송 대상 제한 | 쇼핑몰의 메일 발송 설정 확인 필요 |
| 확인 메일 발송 한도 | 잠시 후 재시도 |
| 신규 가입 중단 | 현재 가입할 수 없음을 안내 |

Supabase가 계정 존재 여부 보호를 위해 가입 요청을 성공으로 응답한 경우에는 중복 여부를 임의로 추측하지 않습니다. 알 수 없는 오류도 특정 입력이 잘못됐다고 단정하지 않습니다. 개발자 로그에는 작업 종류·상태·알려진 오류 식별값만 남기며 이메일·비밀번호·토큰이나 오류 원문은 남기지 않습니다.

근거: [Supabase Auth 오류 종류](https://supabase.com/docs/guides/auth/debugging/error-codes).

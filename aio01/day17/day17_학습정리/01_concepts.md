# 01. 무엇을 만드는 코드인가? 개념과 활용 예시

## 1. 최종 목표: 질문하면 답하는 로컬 학습 도우미

예를 들어 브라우저에 “광합성을 초등학생에게 설명해 줘”라고 입력하면, 내 컴퓨터에 저장된 Qwen 모델이 답변을 만듭니다. day17은 이 기능을 단계적으로 확장하는 실습입니다.

**로컬**은 내 컴퓨터에서 처리한다는 뜻입니다. **언어 모델**은 글을 입력받아 다음에 이어질 글을 계산하도록 학습된 AI입니다. **추론**은 이미 학습된 모델로 결과를 만드는 과정입니다. 이 코드들은 모델을 새로 학습시키거나 인터넷을 검색하지 않습니다.

| 단계 | 추가되는 기능 | 사용자에게 좋은 점 | 예시 |
|---|---|---|---|
| `main1.py` | 화면과 모델 실행 | 작은 앱을 빠르게 실습 | 한 번 질문하고 답 읽기 |
| `backend/` | 화면과 AI 서버 분리 | 같은 AI 기능을 여러 화면에서 사용 가능 | 웹 화면과 다른 프로그램이 같은 API 이용 |
| `stream_backend/` | 생성 중 답변 전송 | 완성 전에 읽기 시작 | 답변이 점차 늘어나는 채팅 |
| `dig_context_backend/` | 대화 이력 전달 | 앞 질문을 참고하는 후속 질문 가능 | “그걸 더 쉽게 설명해 줘” |

여러 화면에서 API를 사용할 수 있다는 것은 구조의 활용 가능성입니다. 현재 서버는 한 프로세스 안에서 모델 생성 요청 하나만 허용하므로 여러 답변을 동시에 만드는 서버는 아닙니다.

## 2. 모델, 가중치, 다운로드, 로딩

**가중치**는 모델이 학습하면서 얻은 수치들입니다. 모델 폴더의 `.safetensors` 파일이 이 수치들을 보관합니다. `config.json`은 모델 구조 등의 설정이고, `tokenizer.json` 등의 파일은 글과 숫자를 바꾸는 규칙을 담습니다.

모델 다운로드와 로딩은 다릅니다.

- **다운로드**: 인터넷의 모델 파일을 디스크에 저장합니다. 책을 서점에서 사서 책장에 꽂는 것과 비슷해요.
- **로딩**: 저장된 파일을 읽어 메모리에 모델을 준비합니다. 책장에서 책을 꺼내 펼치는 것과 비슷해요.
- **추론**: 준비된 모델에 질문을 넣어 답을 만듭니다. 펼친 책을 활용해 문제를 푸는 단계에 해당해요.

같은 모델 파일을 여러 코드가 공유할 수 있습니다. 하지만 서버를 여러 개 실행하면 각각 메모리에 모델을 올릴 수 있어 메모리 사용량은 늘어납니다. 파일 공유와 메모리 공유는 별개입니다.

사용 도구: 다운로드는 `huggingface_hub.snapshot_download()`, 로딩은 Transformers의 `from_pretrained()`, 계산은 PyTorch의 `torch`가 담당합니다. `local_files_only=True`는 로딩할 때 로컬 파일만 사용한다는 뜻입니다.

## 3. 토큰, 토크나이저, 텐서

모델은 문장을 사람이 읽는 글자 그대로 계산하지 않습니다.

```text
질문 문장 → 토크나이저 → 토큰 번호들 → 모델 계산 → 결과 토큰 번호들 → 글로 복원
```

**토큰**은 모델이 글을 처리하는 단위입니다. 한 글자·한 단어와 항상 같지 않습니다. 예를 들어 “안녕하세요”가 몇 토큰인지는 해당 모델의 토크나이저 규칙에 따라 달라요.

**토크나이저**는 글을 토큰 번호로 바꾸고 다시 글로 복원하는 도구입니다. 서로 같은 뜻을 이해할 수 있게 바꾸는 통역 도구에 비유할 수 있습니다.

**텐서**는 숫자를 일정한 모양으로 묶은 자료입니다. 표나 숫자 목록을 확장한 개념으로 생각하면 됩니다. 이 코드의 `return_tensors="pt"`는 PyTorch가 계산할 수 있는 숫자 묶음을 달라는 뜻입니다.

왜 필요한가요? 모델이 계산 가능한 숫자로 질문을 표현해야 하기 때문입니다. `apply_chat_template()`은 모델이 기대하는 대화 형식까지 적용합니다.

코드에는 질문 500자, 모델 입력 512토큰, 새 답변 최대 96토큰 등의 제한이 있습니다. 이들은 서로 다른 기준입니다. 500자 이내라도 토큰 제한에 걸릴 수 있으며, 대화 이력이 있으면 이력과 system 지시도 입력 토큰에 포함됩니다. 이 숫자는 현재 실습 코드의 제한이지 모델 전체의 최대 능력을 뜻하지 않습니다.

## 4. 화면과 백엔드: 주문받는 곳과 요리하는 곳

**사용자 화면(UI)**은 사람이 보고 입력하는 부분입니다. **프런트엔드**는 사용자와 상호작용하는 부분을 뜻합니다. 이 실습에서는 Streamlit 앱이 화면 역할을 맡습니다. Streamlit 자체도 Python 서버에서 실행되며, 브라우저에는 그 화면이 표시됩니다.

**백엔드**는 질문 처리와 모델 실행 같은 일을 담당합니다. 음식점으로 비유하면 화면은 주문을 받는 곳, 백엔드는 요리하는 주방입니다.

`main1.py`는 주문 접수와 요리를 한곳에서 합니다. 작고 단순한 실습에 편합니다. `backend/`부터는 화면과 주방을 분리합니다. 화면을 바꿔도 모델 처리 코드를 유지하기 쉽고, 다른 앱에도 같은 AI 기능을 제공할 수 있습니다. 대신 두 프로그램을 실행하고 주소를 맞춰야 합니다.

## 5. API, HTTP, JSON, 주소와 포트

**API**는 프로그램이 다른 프로그램의 기능을 사용하기 위한 약속입니다. 이 실습의 약속은 “`/chat` 주소로 `prompt`를 보내면 `answer`를 돌려준다”입니다.

**HTTP**는 요청과 응답을 주고받는 통신 규칙입니다. **POST**는 여기서 질문 데이터를 본문에 담아 서버로 보내는 요청 방식입니다. **엔드포인트**는 기능을 제공하는 주소 경로입니다. 일반 버전은 `/chat`, 스트리밍 버전은 `/chat/stream`입니다.

**JSON**은 프로그램끼리 데이터를 전달하는 글자 형식입니다. Python 딕셔너리와 모양이 비슷하지만 같은 자료형은 아닙니다. 네트워크에서는 JSON으로 보내고, `response.json()`으로 Python 자료로 바꿉니다.

```json
{"prompt": "광합성이 뭐야?"}
```

```json
{"answer": "식물이 빛을 이용해 양분을 만드는 과정입니다."}
```

`http://127.0.0.1:8000/chat`에서 `127.0.0.1`은 내 컴퓨터, `8000`은 프로그램을 구분하는 **포트**, `/chat`은 기능 경로입니다. 같은 건물 안의 호수처럼 포트가 서비스를 구분합니다. Streamlit 화면은 기본적으로 8501, FastAPI 서버는 이 명령 구성에서 8000을 사용합니다.

화면 쪽의 `requests.post()`가 요청을 보내고, 서버의 `@app.post()`가 받을 함수를 등록합니다. FastAPI는 접수 규칙을 만들며, Uvicorn은 요청을 기다리고 앱을 실행하는 서버 역할을 합니다. `/docs`는 채팅 화면이 아니라 API를 직접 시험하는 문서 화면입니다.

## 6. 검증: 데이터에도 주문서 양식이 필요하다

**검증**은 받은 데이터가 약속한 조건을 만족하는지 확인하는 일입니다. 예를 들어 질문에는 글자 문자열이 와야 하고, 빈 질문은 받지 않아야 합니다.

Pydantic의 `BaseModel`과 `Field()`로 이 규칙을 선언합니다. 화면에서도 길이를 검사하지만, 서버에서도 검사해야 다른 프로그램이 화면을 거치지 않고 요청해도 같은 규칙을 적용할 수 있습니다.

`ChatRequest`는 질문 양식, `ChatResponse`는 답변 양식입니다. 여기서 Pydantic의 “모델”은 **데이터 양식**이며, Qwen 같은 **AI 모델**과 다른 의미입니다.

대화 이력 버전은 역할을 `user` 또는 `assistant`로 제한하고, 질문과 답변이 번갈아 나오며 마지막은 질문인지 검사합니다. 표지와 페이지 순서를 검사하는 책 제본 검사에 비유할 수 있어요.

## 7. 캐시와 서버 수명: 무거운 준비를 반복하지 않기

**캐시**는 준비한 결과나 자원을 보관했다가 재사용하는 방법입니다. Streamlit은 사용자 조작 시 코드를 다시 실행할 수 있으므로, 매번 무거운 모델을 로딩하면 비효율적입니다. `main1.py`의 `@st.cache_resource`는 준비된 모델을 재사용합니다. 이 코드에서는 질문을 처음 처리할 때 모델 로딩 함수가 호출됩니다.

FastAPI 쪽은 **수명 관리(lifespan)**를 사용합니다. `yield` 앞에서 서버 시작 준비를 하고, 서버가 요청을 처리하는 동안 모델을 유지하며, 정상 종료 때 뒤쪽 정리를 합니다.

```text
서버 시작 → 모델 한 번 준비 → 여러 요청 처리 → 서버 종료 때 참조 정리
```

이 캐시는 답변을 외워 같은 답을 재사용하는 기능이 아닙니다. 또한 “모델 재사용”과 “대화 기억”은 다릅니다.

## 8. `return`, `yield`, 제너레이터

`return`은 결과를 반환하고 함수 실행을 끝냅니다. `yield`는 값을 하나 건네고 실행 위치를 보관합니다. 다음 값을 요구하면 이어서 진행합니다. 이런 함수를 호출하면 **제너레이터**, 즉 값을 차례로 만들어 주는 객체가 생깁니다.

`main_yield.py`는 숫자 하나를 준비하는 데 1초씩 걸린다고 가정합니다.

| 방식 | 관찰하는 흐름 | 활용 |
|---|---|---|
| 리스트를 만든 후 `return` | 약 3초 뒤 1, 2, 3을 받음 | 결과 전체가 필요한 작은 작업 |
| 숫자마다 `yield` | 약 1초마다 다음 숫자를 받음 | 긴 파일 읽기, 많은 데이터 순회, 답변 스트리밍 |

둘 다 숫자 세 개를 만드는 시간은 비슷합니다. `yield`가 전체 계산을 자동으로 빠르게 해 주는 것은 아닙니다. 결과를 일찍 받기 시작하고, 전체 목록을 한꺼번에 만들지 않을 수 있다는 점이 장점입니다.

이 예제의 `time.sleep(1)`은 설명용 대기입니다. 실제 AI 스트리밍 코드는 `sleep()`으로 글자 출력 속도를 꾸미는 것이 아니라 생성 중인 텍스트를 전달합니다.

lifespan의 `yield`도 실행을 잠시 넘긴다는 원리는 같지만, 여기서는 **답변 조각 전송이 아니라 서버의 준비와 정리 경계**를 표현합니다.

## 9. 스트리밍: 답변이 완성되기 전에 읽기

**스트리밍**은 결과를 조각 단위로 계속 전달하는 방식입니다. 전체 동영상 다운로드를 기다리지 않고 재생하는 것과 비슷합니다.

`stream_backend/`는 모델이 만드는 텍스트 조각을 즉시 받을 수 있게 연결합니다. 다만 네트워크 버퍼와 디코딩 때문에 한 글자 또는 한 토큰씩 반드시 도착하는 것은 아닙니다. 첫 내용을 일찍 볼 수 있지만, 전체 답변 생성 시간이 반드시 줄지는 않습니다.

```text
model.generate()가 생성 중 텍스트 전달
   → TextIteratorStreamer가 읽을 수 있는 글 조각 제공
   → stream_events()가 조각을 JSON 한 줄로 포장
   → StreamingResponse가 HTTP 응답 본문으로 전송
   → requests.iter_lines()가 줄별로 수신
   → request_stream()이 글 조각을 yield
   → st.write_stream()이 화면에 이어 붙임
```

`TextIteratorStreamer`는 Transformers의 생성 결과를 반복해서 읽을 수 있게 연결하는 도구입니다. `st.write_stream()`은 전달받은 텍스트 조각들을 차례로 보여 줍니다. [Transformers 생성 도구 설명](https://huggingface.co/docs/transformers/v4.57.1/en/internal/generation_utils#transformers.TextIteratorStreamer), [Streamlit 공식 설명](https://docs.streamlit.io/develop/api-reference/write-magic/st.write_stream)

### NDJSON과 완료 신호

**NDJSON**은 JSON 객체 하나를 한 줄씩 보내는 형식입니다. 이 코드는 다음처럼 보냅니다.

```json
{"type":"delta","text":"광합성은 "}
{"type":"delta","text":"식물이 빛으로 양분을 만드는 과정입니다."}
{"type":"done"}
```

`delta`는 새로 도착한 글 조각, `done`은 정상 완료 신호입니다. 줄바꿈으로 객체의 경계를 구분하므로 네트워크 조각이 임의의 위치에서 나뉘어도 한 줄을 모아 해석할 수 있습니다. 중간 글을 받았다는 것과 답변이 완성됐다는 것을 구분하는 장점이 있어요.

이 구현은 SSE나 WebSocket이 아니라 `application/x-ndjson` 응답입니다. FastAPI의 `StreamingResponse`는 반복자에서 나온 조각을 응답으로 전달하는 데 사용합니다. [FastAPI 공식 설명](https://fastapi.tiangolo.com/advanced/custom-response/#streamingresponse)

## 10. 스레드, 큐, 락: 생성과 전달을 함께 진행하기

**스레드(Thread)**는 한 프로그램 안에서 작업 흐름을 따로 실행하는 방법입니다. 이 코드에서는 한쪽이 모델 답변을 만들고, 다른 쪽이 만들어진 조각을 받아 전달합니다. 요리하는 사람과 완성된 접시를 내보내는 사람에 비유할 수 있어요. 스레드를 쓴다고 모든 계산이 자동으로 빨라지는 것은 아닙니다.

**큐(Queue)**는 먼저 들어온 것을 먼저 꺼내는 대기 줄입니다. `TextIteratorStreamer` 내부에서 생성 측과 읽는 측 사이를 연결합니다. 다음 글 조각이 없으면 기다리고, 제한 시간 동안 없으면 `queue.Empty`로 대기 종료를 알립니다.

**락(Lock)**은 공유 자원을 한 번에 한 작업만 사용하도록 하는 잠금입니다. 현재 백엔드는 모델 사용 중 다른 요청이 오면 기다리게 쌓지 않고 거절합니다. 동일 프로세스 안의 잠금이며 서버 여러 프로세스 전체를 하나로 잠그는 것은 아닙니다.

왜 필요한가요? 한정된 CPU와 모델을 사용하는 실습에서 생성 작업이 겹치는 것을 제어하고, 생성과 전송 흐름을 분리하기 위해서입니다. `worker.start()`는 별도 흐름을 시작하고, `worker.join()`은 작업이 끝나기를 기다립니다. 타임아웃이나 브라우저 종료가 CPU 생성 작업을 자동으로 강제 중단하는 것은 아닙니다.

## 11. 대화 이력과 문맥: 기억은 입력을 다시 보내서 만든다

**문맥(context)**은 지금 질문을 이해하는 데 함께 참고하는 정보입니다. **대화 이력**은 이전 질문과 답변의 목록입니다.

예를 들어 다음 질문은 앞 대화가 있어야 뜻을 이해하기 쉽습니다.

```text
사용자: 광합성이 뭐야?
AI: 식물이 빛으로 양분을 만드는 과정입니다.
사용자: 그럼 밤에도 할 수 있어?
```

`backend/`와 `stream_backend/`는 현재 질문만 보냅니다. `dig_context_backend/`는 앞 질문과 답변도 함께 보내므로 “그럼”이 무엇을 가리키는지 참고할 수 있습니다. 작은 모델이 항상 정확히 이해한다는 보장은 없습니다.

각 메시지는 `role`과 `content`로 구성됩니다.

- `system`: 답변 방식 지시. 이 코드에서는 서버가 “한국어로 짧고 쉬운 문장으로 답하세요”를 추가합니다.
- `user`: 사람의 질문.
- `assistant`: 모델의 이전 답변.

이력은 화면의 `st.session_state.messages`에 보관합니다. **세션 상태**는 같은 브라우저 세션에서 코드가 다시 실행돼도 값을 이어 쓰는 저장 공간입니다. 영구 저장용 데이터베이스가 아니며, 이 코드는 새로고침·연결 종료 후에도 이력을 보존하는 기능을 구현하지 않습니다.

중요한 차이는 다음과 같습니다.

| 기능 | 하는 일 |
|---|---|
| 화면에 이력 표시 | 사람이 지난 대화를 다시 읽게 함 |
| 요청에 이력 포함 | 모델이 지난 대화를 참고하게 함 |
| 모델 재학습 | 모델의 학습된 수치 자체를 바꿈. 이 실습에서는 하지 않음 |

백엔드는 사용자별 이력을 따로 저장하지 않습니다. 매 요청의 `messages`를 받아 사용할 뿐입니다. 현재 UI는 최대 다섯 질문·답변 쌍까지 유지하며, 다섯 번째 요청에는 과거 네 쌍과 현재 질문인 최대 9개 메시지를 보냅니다. 입력 전체는 별도로 512토큰 제한을 받으므로 다섯 번 전에 한도에 도달할 수 있습니다.

`candidate`는 기존 이력에 새 질문을 붙인 임시 목록입니다. 정상 완료된 답변이 있을 때만 질문·답변 한 쌍을 원래 이력에 반영합니다. 임시 작업 후 성공하면 확정하는 방식이라 대화 순서를 유지하기 좋습니다. “새 대화” 버튼은 이 목록을 비우며, 모델을 새로 학습시키거나 가중치를 초기화하지 않습니다.

## 12. 설정 파일과 Python 환경

**환경변수**는 프로그램 바깥에서 주는 설정값입니다. `.env`는 이를 `이름=값` 형태로 적는 설정 파일입니다. 모델 경로나 서버 주소를 코드에 고정하지 않고 바꿀 때 편리합니다. `.env`는 모델 파일 자체를 담는 곳이 아닙니다.

**상대 경로**는 기준 폴더에서 출발하는 주소이고, **절대 경로**는 전체 주소입니다. `Path(__file__).resolve().parent`는 실행한 터미널 위치가 아니라 해당 소스 파일이 있는 폴더를 가리킵니다. `expanduser()`는 `~`를 사용자 홈 경로로 바꿉니다. 상대 경로를 뜻하는 함수는 아닙니다.

**Python 환경**은 Python 실행기와 설치 패키지를 따로 묶어 관리하는 공간입니다. 수업별 도구 상자처럼 생각하면 됩니다. 코드 파일은 환경 밖에 있어 같은 파일을 여러 환경에서 실행할 수 있습니다.

`py313`과 `py313_arm`처럼 환경을 나누면 기존 수업 도구를 유지한 채 새로운 패키지 구성을 사용할 수 있습니다. ARM64와 x86_64는 CPU 명령 체계의 구분입니다. Apple Silicon의 기본 실행 체계는 ARM64이고, Intel용 Python은 호환 실행을 사용할 수 있습니다. 일부 패키지는 이 체계에 맞는 설치 파일이 필요합니다. 환경 이름은 표시용 이름이므로 실제 체계를 보장하지 않습니다.

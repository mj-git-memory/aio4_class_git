## 🚀 이걸 배우면 무엇을 만들 수 있을까?

**Day22~25는 “자료를 읽고 답변하기 → 필요한 계산·조회 실행하기 → 정해진 형식으로 결과 받기 → 잘못된 실행을 막고 점검하기”를 배우는 과정입니다.**

고객이 질문할 때마다 사람이 자료를 찾고, 계산하고, 표를 채우는 일을 작은 AI 프로그램으로 연결하는 데 활용할 수 있습니다. 아래 서비스는 현재 코드로 확인되는 기능과, 그 코드를 바꿔 만들 수 있는 응용을 구분했습니다. 이 문서를 추가하면서 서비스를 새로 구현한 것은 아닙니다.

### 1. 날짜별로 “왜 배우는가”부터 보기

| 날짜 | 해결하려는 문제 | 배우면 할 수 있는 일 | 가장 중요한 도구 |
| --- | --- | --- | --- |
| Day22 | 질문마다 자료를 복사해 붙이고 같은 지시를 반복함 | 자료와 질문을 자동으로 조합해 일정한 처리 순서로 답변 생성 | `ChatPromptTemplate`, `RunnableLambda`, `build_chain()` |
| Day23 | 여러 단계 계산에서 무엇을 언제 실행해야 할지 결정해야 함 | AI가 계산을 요청하고 Python 결과를 읽어 다음 작업을 이어가는 프로그램 구성 | `react()`, `calculate()`, `json.loads()` |
| Day24 | 답변을 표·DB에 쓰려면 필드가 일정해야 하고, 사내 사실은 조회가 필요함 | 입력을 정해진 데이터로 변환하거나, 자연어로 DB 조회·집계 후 설명 | Pydantic, `query_database()`, `run_pipeline()` |
| Day25 | 잘못된 할인 지시를 적용하거나, 어느 단계에서 틀렸는지 모름 | 계산 조건을 코드로 제한하고 실행 기록·평가로 문제 지점을 찾기 | `@tool`, 함수 내부 검증, `@traceable`, `evaluate()` |

**처음에는 함수 이름을 외우기보다 “자료 준비 / 모델에게 지시 / 실제 실행 / 결과 검사” 중 어느 역할인지 구분하는 것이 중요합니다.**

### 2. 만들 수 있는 서비스 ① — 상품 문의 답변 초안 도우미

**누가 쓰나?** 상품 설명을 보고 고객 문의에 답하는 판매자·상담 담당자.

**어떤 일을 줄이나?** 상품 설명을 찾고, 고객 질문과 연결하고, 모르는 정책을 따로 표시하는 반복 작업.

**입력 → 처리 → 출력 예시**

```text
입력: 상품 ID + “15인치 노트북이 들어가나요? 반품은요?”
처리: 해당 상품 설명 찾기 → 설명과 질문을 지침에 넣기 → 초안 생성
출력 예시: 수납 근거 안내 + “반품 정책은 별도 확인이 필요합니다.”
```

출력 문장은 동작을 설명하는 예시이며 이번에 새 AI 응답을 생성한 결과는 아닙니다.

| 필요한 기능 | 기존 코드·함수 | 쉬운 역할 |
| --- | --- | --- |
| 상품 자료 읽기 | `read_catalog()` | 상품 파일을 목록으로 읽는 담당 |
| 대상 상품 찾기 | `find_product(records, record_id)` | ID에 맞는 상품 카드 선택 |
| 믿을 자료 준비·질문 검사 | `product_context()`, `prepare_input()` | 원문에서 쓸 필드만 고르고 빈 질문 거절 |
| 답변 양식·규칙 구성 | `ChatPromptTemplate.from_messages()`, `get_prompt()` | 상담원의 역할·근거·말투를 지정 |
| 전체 과정 연결 | `build_chain()`, `.invoke(request)` | 입력부터 답변까지 순서대로 실행 |
| 여러 문의 처리·저장 | `.batch()`, `save_report()`, JSONL 저장 | CSV 문의 여러 건의 초안을 모으기 |

**현재 코드에 있는 것:** 상품 ID 기반 선택, 템플릿·체인, CSV 일괄 처리, 결과 파일 저장.

**응용할 때 추가할 것:** 내 상품 자료로 교체하고 필드를 맞추기. 상품명 검색, PDF 문서 검색, 실시간 재고·배송 조회, 고객 채팅 화면은 별도 기능으로 추가해야 합니다. 지금 카탈로그에 없는 정보를 자동으로 조회하는 구조는 아닙니다.

**이걸 배우는 이유:** 매번 복사·붙여넣기하던 “자료와 질문을 준비하는 과정”을 재사용 가능한 함수로 만들 수 있기 때문입니다.

### 3. 만들 수 있는 서비스 ② — 견적·할인·환산 계산 도우미

**누가 쓰나?** 주문 금액·할인·환산을 순서대로 계산해야 하는 담당자.

**입력 → 처리 → 출력 예시**

```text
입력: “단가 25,000원, 4개, 10% 할인. 1달러=1,400원으로 환산해줘.”
처리: 25,000 × 4 → 100,000원
      100,000 × (1 - 0.1) → 90,000원
      90,000 ÷ 1,400 → 64.29달러
출력: 할인 전 100,000원 / 할인 후 90,000원 / 환산 64.29달러
```

계산값은 앞서 원본 계산 함수 본체로 확인한 값입니다. AI가 이 세 도구를 올바른 순서·인수로 요청하는지는 별도로 확인해야 합니다.

| 필요한 기능 | 기존 코드·함수 | 쉬운 역할 |
| --- | --- | --- |
| 계산할 다음 행동 결정 | Day23 `react()` | 결과를 보고 다음 계산을 이어감 |
| 기본 계산 | Day23 `calculate(action, a, b)` | 더하기·빼기·곱하기·퍼센트 계산 |
| 모델에게 계산 기능 제공 | Day25 `@tool`, `llm.bind_tools(TOOLS)` | 사용할 계산 도구 목록을 알려줌 |
| 주문 계산 | `multiply()`, `apply_discount()`, `convert_currency()` | 수량·할인·환산의 실제 계산 |
| 계산 결과 다시 전달 | `ToolMessage(..., tool_call_id=...)` | 어떤 계산 요청의 결과인지 연결 |
| 비정상 조건 거절 | `apply_discount()` 등의 범위 검사 | 허용하지 않는 할인율이면 오류 |

**현재 코드에 있는 것:** 수학 문제용 ReAct 루프, 주문 계산용 도구 루프, 일부 파일의 할인율·환율 검증.

**응용할 때 추가할 것:** 회사 할인 정책·상품 가격을 신뢰할 저장소에서 가져오기, 수량·금액 등의 추가 검증, 필요하면 환율 조회 기능. 현재 환율은 전달한 숫자·기본값이고, 주문 확정·결제·견적서 발송 기능은 없습니다.

**이걸 배우는 이유:** AI가 말로만 계산 결과를 작성하는 단계에서 나아가, 실제 계산 함수를 실행하고 그 결과를 다음 처리에 사용할 수 있기 때문입니다. 함수가 정확해도 인수 선택이 틀릴 수 있으므로 요청과 실행 결과를 함께 봅니다.

### 4. 만들 수 있는 서비스 ③ — 자연어 업무 데이터 조회 도우미

**누가 쓰나?** SQL을 직접 작성하기 어려운 업무 담당자.

**입력 → 처리 → 출력 예시**

```text
입력: “E001의 이번 달 법인카드 사용 건수와 총액을 표로 알려줘.”
처리: 대상·기간·요구 항목 분석
      → Gemini가 SQL과 인수를 요청
      → Python이 SQLite에서 COUNT·SUM 조회
      → OpenAI가 실제 조회 결과를 표로 설명
출력: 직원 / 조회 기간 / 사용 건수 / 총액
```

건수·금액은 실제 DB에 따라 달라집니다. 조회하지 않은 수치를 예시 정답처럼 만들지 않습니다.

| 필요한 기능 | 기존 코드·함수 | 쉬운 역할 |
| --- | --- | --- |
| 질문을 업무 조건으로 정리 | `analyze_intent()` | 누구·언제·무엇을 찾는지 추출 |
| 조건 구조 검사 | `IntentAnalysis.model_validate_json()` | 빠진 항목·잘못된 자료형 검사 |
| “이번 달” 해석 | `relative_period_rules()`, `calendar.monthrange()` | 달력 날짜 범위 계산 |
| 도구 요청 검증·조회 | `execute_tool()`, `query_database()` | 등록한 도구만 실행해 DB 읽기 |
| 건수·총액·순위 계산 | SQL `COUNT`, `SUM`, `GROUP BY`, `ORDER BY` | DB에서 집계 수행 |
| 결과 설명 | `generate_final_answer()` | 실제 결과를 문장·표로 정리 |
| 전체 순서·실패 처리 | `run_pipeline()` | 조회 실패 시 답변 생성을 중단하고 근거 보존 |

**현재 코드에 있는 것:** 가상 직원·카드 데이터, 읽기 전용 SQL 조회, 조건 분석, 두 모델 간 결과 전달.

**응용할 때 추가할 것:** 내 DB의 테이블·열에 맞게 스키마와 지침 변경, 로그인·사용자별 조회 권한·민감 필드 제한. “SQL을 읽기 전용으로 실행한다”와 “이 사용자가 연봉 정보를 볼 수 있다”는 별개의 조건입니다.

**이걸 배우는 이유:** 자연어 질문을 실제 데이터 조회와 연결하는 법을 배우기 때문입니다. 같은 구조를 주문 현황·매출·재고 조회로 바꾸려면 DB와 업무 규칙을 새로 맞추면 됩니다.

### 5. 만들 수 있는 서비스 ④ — 문장을 정해진 항목으로 정리하는 입력 도우미

**누가 쓰나?** 상담 메모·접수 내용 등을 표나 DB에 정리하는 사람.

**쉬운 예시 — 아래는 기존 구조화 출력을 확장하는 응용 설계입니다.**

```text
입력: “주문한 상품이 파손돼 도착했어요. 교환하고 싶어요.”
출력 예시:
{
  "category": "파손",
  "requested_action": "교환",
  "summary": "파손 상품 교환 요청"
}
```

| 필요한 기능 | 기존에 배운 함수·기능 | 새로 정할 부분 |
| --- | --- | --- |
| 받을 항목 정의 | `BaseModel`, `Literal`, `ConfigDict` | 상담용 모델과 허용 분류 |
| AI에 형식 전달 | `.with_structured_output(모델, ...)` | 추출 지침·예시 |
| 결과 형식 검사 | `.model_validate_json()` | 필수 필드·자료형·허용값 |
| dict로 사용·저장 | `.model_dump()`, `json.dumps()` | CSV·DB 연결 |
| 내용 정확성 확인 | 원본 대조 원리 | 분류·요약의 평가 사례와 사람 확인 기준 |

**현재 코드에 있는 것:** 은행 CSV·상품 데이터를 정해진 구조로 변환하고 원본과 대조하는 기능.

**응용할 때 추가할 것:** 상담용 스키마·프롬프트·평가 데이터. 원본을 그대로 옮기는 데이터와 달리 요약·분류는 정답 기준이 필요합니다. Pydantic 검사 통과만으로 내용이 정확하다고 판단하지 않습니다.

**이걸 배우는 이유:** AI 출력이 일정한 항목을 가져야 다음 코드가 표를 만들고 DB에 저장하고 업무별로 분기할 수 있기 때문입니다.

### 6. Day25는 위 서비스를 점검·개선하는 데 쓰기

Day25의 가치는 “답변 한 번 만들기”를 넘어, 서비스가 어떤 요청에서 잘못 동작하는지 확인하는 데 있습니다.

| 하고 싶은 점검 | 사용할 기능 | 확인할 질문 |
| --- | --- | --- |
| 잘못된 할인 요청 거절 | 도구 내부 `if` 검사·`raise ValueError` | 실제 금액 계산 전에 거절됐나? |
| 외부 문구와 실행 규칙 구분 | 시스템 지침·입력 경계·검증 코드 | 상품 메모 속 지시를 규칙으로 받아들이지 않았나? |
| 틀린 단계 찾기 | `@traceable`, tags·metadata | 모델 선택·도구 인수·계산·최종 설명 중 어디서 틀렸나? |
| 수정 전후 비교 | `evaluate()`, 데이터셋·평가 함수 | 같은 질문 묶음에서 무엇이 좋아지고 나빠졌나? |

현재 `score_no_leak_or_bypass()`는 특정 문자열 유무를 검사하는 작은 평가자입니다. 견적 서비스에는 **계산 정답 평가**, 조회 서비스에는 **DB 결과와 수치 일치 평가** 등을 추가해야 합니다. 추적은 기록, 평가는 판정이며 둘은 역할이 다릅니다.

### 7. 하나로 연결하면 — 상품 상담 + 주문 금액 안내 도우미

아래는 네 날짜의 기술을 합친 **확장 설계**입니다. 현재 폴더들이 이 서비스 하나로 연결되어 있다는 뜻은 아닙니다.

```text
고객 질문
  ↓
질문 종류와 필요한 항목 정리                  ← Day24 스키마·의도 분석
  ↓
상품 설명 문의 → 카탈로그에서 근거 준비       ← Day22
금액 계산 문의 → 계산 도구 실행              ← Day23·25
주문 현황 문의 → 권한 확인 뒤 DB 조회        ← Day24 + 별도 권한 기능
  ↓
실제 자료·도구 결과로 답변 작성               ← Day22·24
  ↓
규칙 검사·실행 추적·테스트 질문으로 평가      ← Day25
```

이 흐름을 만들려면 공통으로 네 가지를 정합니다: **어떤 입력을 받을지, 어느 자료를 믿을지, 어떤 함수만 실행할지, 무엇을 성공으로 판단할지.**

### 8. 처음 직접 만들어볼 범위

전체를 한 번에 연결하기보다 **“상품 하나에 대한 문의 초안 만들기”**부터 시작하면 날짜별 기술의 역할을 확인하기 쉽습니다.

1. **Day22:** 상품 3개와 질문 1개로 초안 생성. `prepare_input()`·`build_chain()`부터 읽기.
2. **Day24 A:** 결과를 `답변 / 근거 / 확인 필요 항목`으로 받는 새 스키마 추가.
3. **Day25:** 단가×수량 계산 도구 1개를 붙이고 허용 입력 범위 검사.
4. **Day23:** 계산 결과가 다음 계산에 전달되는 순서를 확인.
5. **Day25:** 정상·빈 입력·없는 상품·잘못된 할인 요청의 예상 결과를 정해 비교.

처음에는 웹 화면 없이 터미널 입력·출력으로도 충분합니다. **완료 기준은 “질문 하나가 어떤 자료와 함수를 거쳐 결과가 되는지 설명하고, 실패 사례 하나를 확인할 수 있는가”입니다.**

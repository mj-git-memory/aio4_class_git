API 설정과 비용 범위

.env의 OPENAI_API_KEY, OPENAI_MODEL을 제공받은 계정의 키와 사용 가능한 모델 ID로 바꾼다. LLM_PROVIDER=openai가 기본이다. LLM_TEMPERATURE는 미설정일 때 전달하지 않으며 해당 파라미터를 지원하는 모델에서만 지정한다. 키는 코드나 결과 화면에 표시하지 않는다.

Groq 선택 실습은 python -m pip install -r requirements-groq.txt 후 LLM_PROVIDER=groq, GROQ_API_KEY, GROQ_MODEL을 지정한다. 무료 플랜에도 모델별·조직별 한도가 있다. 두 공급자의 모델 지원·가격·한도는 수업 전 공식 콘솔에서 확인한다. 공급자 전환은 자동으로 일어나지 않는다.

1~3차시는 모델 요청이 없다. 4~5차시는 기본 명령당 1회, 6차시 batch는 3회·stream은 1회, 7차시는 기본 9회(최대 27회), 8차시는 기본 최대 3회다. 정상 경로 기본 실행을 한 번씩 하면 총 17회이며 수동·스트리밍·재실행·선택 실습은 추가다. 출력 상한은 요청당 500토큰 설정이며 모델별 지원은 별도로 확인한다. 자동 재시도는 0회다. 429가 나면 계정 한도를 확인하고 대기 후 수동으로 재실행한다. batch는 입력당 호출이 발생하며 공급자의 할인 Batch API와 다르다.

오늘 만들 프로젝트

상품 설명을 보고 고객 질문에 답하는 상품 안내 초안 서비스를 만든다. 예를 들어 가방에 15인치 노트북을 넣을 수 있는지 묻는 고객에게 상품 설명에서 근거를 찾아 한국어로 안내한다. 그러나 상품 설명에 재고·배송일·반품 정책이 없으면 답을 만들지 않고 추가 확인이 필요하다고 알려야 한다.

서비스의 처리 경로는 상품 JSON 읽기 → 상품 선택 → 메시지 구성 → 모델 호출 → 텍스트 추출 → 결과 화면 저장이다. LangChain은 이 경로를 구성하는 도구이고, 자연어를 생성하는 주체는 선택한 공급자의 모델이다. 이번에는 검색 엔진·RAG·Function Calling을 추가하지 않는다. 선택할 상품은 Python이 명시적으로 고른다.

LangChain은 기능별 패키지로 나뉜다. 템플릿·LCEL 수업에서는 Core와 OpenAI 통합을 사용한다. 상위 에이전트용 langchain 패키지나 LangGraph가 아직 필요하지 않다. 패키지 설치는 모델 다운로드가 아니다. 원격 API를 쓰려면 별도의 키·모델 접근 권한·네트워크가 필요하다.

이번 상품 데이터의 범위를 정확하게 읽기

기관 안내 목록의 D01은 Fake Store API다. 현재 제작 환경에서는 원본 API가 보안 확인/403으로 막혀 직접 응답을 확보하지 못했다. 실행 가능한 교안에는 Fake Store에서 데이터를 가져왔다고 명시한 공개 프로젝트의 가공 상품 파일 20개를 고정해 포함했다. 이 파일을 공식 API의 최신 응답이라고 부르지 않는다.

가공 파일에는 title, category, description, price, image가 있고 공식 상품 id와 rating은 없다. 따라서 원문 행 번호로 row-001 같은 로컬 추적 id를 부여한다. 이 값은 API id가 아니다. 가격은 공개 가공본에서 바뀌었을 수 있고 통화도 확인되지 않아 모델 맥락에서 제외한다. 상품 사진은 내려받지 않으며 보고서에 이미지 URL 텍스트만 남긴다.

원본 API를 수집할 수 있는 학생 환경에서는 python -m app.fetch_products를 실행해 data/products_live.json을 저장하고 이후 명령에 --data data/products_live.json을 붙인다. 이미 브라우저에서 응답을 저장했다면 python -m app.fetch_products --import-file 저장한파일.json을 사용한다. 가져온 파일의 출처는 독립 검증된 API 직접 수집과 구분해 기록한다. 보안 확인을 우회하지 않는다.

JSON과 Python 자료형

JSON은 데이터 교환 형식이고 Python 객체 그 자체가 아니다. json.loads() 또는 json.load()로 읽으면 JSON 배열은 list, 객체는 dict, 문자열은 str가 된다. 이번 상품 목록은 list[dict]다. 상품 하나를 고른 뒤에는 product["title"]처럼 키로 값에 접근한다. 파일 인코딩은 한국어와 BOM 가능성을 고려해 utf-8-sig로 읽는다.

데이터를 읽었다는 사실과 모델이 답변을 생성했다는 사실은 다르다. 1~3차시는 모델 호출 없이 데이터와 프롬프트 구조를 익힌다. 보고서에도 ‘모델 호출 없음’으로 표시된다.

프로젝트 루트는 app, sessions, requirements.txt가 있는 폴더다. Windows CMD에서는 다음을 차례로 실행한다.

python -m venv .venv

출력에서 상품 수 20, 취득 방식 public_derived_file, row-001의 상품명을 확인한다. 화면 생성 보조 모듈은 미리 제공되며 이번 학습의 대상은 아니다. 그 안에 모델 호출이 숨겨져 있지 않고 이미 나온 결과만 저장한다.

왜 메시지에 역할을 붙일까?

고객의 질문과 애플리케이션의 규칙을 긴 문장 하나에 섞으면 무엇이 지침이고 무엇이 처리 대상인지 읽기 어렵다. 채팅 모델은 역할과 본문을 가진 메시지 목록을 입력으로 받는다. LangChain의 ChatPromptTemplate은 이런 메시지들의 템플릿을 만들고 변수에 값을 넣는다.

from_messages()에 전달하는 목록의 각 튜플은 (역할, 본문 템플릿)이다. 본문에 “나는 시스템이다”라고 적어도 메시지 역할이 바뀌지는 않는다. 역할은 문자열 내용과 분리된 구조적 속성이다.

메시지 역할 이번 서비스에서의 역할
system 상품 안내 업무 지침·사용할 근거
human / user 고객 질문
ai / assistant 이전 모델 답변이나 예시 답변

메시지의 system 역할과 “상담원 역할로 말하라”는 작업 역할은 다르다. 앞의 것은 API에 전달하는 메시지 종류이고, 뒤의 것은 본문 안에 적은 지시다. 이 둘을 나누어야 프롬프트를 수정할 때 구조와 문체를 혼동하지 않는다.

템플릿 변수와 입력 딕셔너리

이번 템플릿의 변수는 role, context, question이다. 상품 설명을 context에 넣고 고객 질문을 question에 넣는다. 세 변수를 받더라도 invoke()에는 딕셔너리 하나를 주 입력으로 전달한다.

values = {
    "role": "상품 안내 도우미",
    "context": product_context(product),
    "question": "노트북을 넣을 수 있나요?"
}
value = prompt.invoke(values)

Python f-string의 f"{role}"은 문자열을 만드는 순간 Python 변수 값을 읽는다. LangChain 템플릿은 일반 문자열 "{role}"로 작성하고 invoke()를 실행할 때 딕셔너리의 값을 넣는다. prompt.input_variables는 템플릿이 요구하는 변수 목록이다.

템플릿 ChatPromptTemplate 역할·본문·빈칸
입력 dict 빈칸에 대응하는 값

prompt.invoke(values)는 가방의 특성을 추론하지 않는다. 상품 설명과 고객 질문을 메시지에 배치할 뿐이다. to_messages()로 실제 전달 내용을 확인할 수 있다. 이 단계는 API 키가 없어도 동작한다.

role이나 context가 빠지면 KeyError가 발생한다. 이는 인증 오류가 아니라 모델 호출 전 입력 계약 오류다. 값을 채우는 단계부터 따로 실행하면 프롬프트 오류와 원격 API 오류를 분리하기 쉽다.

역할 지정만으로 사실이 늘어나지는 않는다

“친절한 상품 상담원입니다”라고 지정하면 문체를 유도할 수 있다. 그러나 그 한 문장으로 상품 재고나 배송일을 알게 되는 것은 아니다. 모델이 쓸 수 있는 근거와 할 수 없는 일을 함께 정해야 한다. 이번 서비스의 목표는 상품 설명에서 확인할 수 있는 특징을 안내하고, 없는 정보는 확인이 필요하다고 말하는 것이다.

Role·Instruction·Context는 프롬프트를 설계하는 관점이다. LangChain의 특별한 세 클래스가 아니라 ‘누가, 무엇을, 어떤 근거로 수행하는가’를 분리해서 생각하는 방식이다.

요소 설계 내용 이번 코드
Role 어떤 업무 관점인가? 상담원 검토용 상품 안내 초안 작성
Instruction 어떤 행동·표현·한계를 지킬까? 근거 밖 사실 금지, 존댓말, 인사→설명→다음 행동
Context 어떤 근거가 있는가? 상품명·분류·설명·추적 id
Question 무엇에 답할까? 고객의 현재 질문

상품 데이터의 price는 보존되어 있지만 이번 맥락에는 없다. 공개 가공본의 값을 현재 판매가나 특정 통화로 단정할 수 없기 때문이다. 보고서의 원문과 모델에 전달한 맥락을 함께 보이면 어떤 정보를 의도적으로 제외했는지 설명할 수 있다.

근거의 범위와 업무 권한

가방 설명에 15인치 노트북 수납이 명시되어 있으면 그 정보를 안내할 수 있다. 반품 조건이 없으면 반품이 가능하다고 단정하지 않는다. 설명의 ‘satisfaction guaranteed’ 같은 광고 문구를 모든 상품의 공통 반품 정책으로 확대하는 것도 피한다. 조회 도구가 없으므로 실제 재고나 주문 상태를 확인했다고 말해서도 안 된다.

이는 텍스트 생성과 업무 실행을 구분하는 설계다. 프롬프트가 어떤 내용을 답할지 유도할 수는 있어도 실제 주문을 조회하거나 환불을 승인하지는 않는다. 도구 호출은 11월 23일 이후에 별도로 구현한다.

LCEL에서는 이 순서를 chain = prompt | model | output_parser로 표현한다. |는 Python의 비트 연산을 그대로 실행하는 것이 아니라 Runnable이 연산자를 재정의하여 순차 실행 객체를 만드는 문법이다. 체인을 만드는 줄에서 요청이 발생하지 않는다. chain.invoke(values)를 호출할 때 실제 처리가 진행된다.

Runnable은 입력을 받아 결과를 돌려주는 부품의 공통 인터페이스다. 부품마다 내부 구현은 다르지만 invoke()로 실행할 수 있어 조합하기 쉽다. 어떤 부품이든 마음대로 붙일 수 있는 것은 아니고 앞의 출력 자료형을 뒤가 받을 수 있어야 한다.

검증 버전에서 파서 결과의 클래스 이름이 TextAccessor로 보일 수 있다. str의 하위 자료형이므로 문자열처럼 사용할 수 있고 str(answer)로 일반 문자열을 얻을 수도 있다. 클래스 이름이 다르게 표시되는 것과 계약이 깨지는 것은 구분한다.

모델 응답과 텍스트의 차이

AIMessage에는 내용뿐 아니라 공급자별 메타데이터와 토큰 사용량이 포함될 수 있다. 문장만 표시하려면 문자열 파서가 편리하다. 사용량을 기록하려면 파서 이전의 메시지를 받아야 하며, 7차시 비교 코드가 그 지점을 사용한다.

파서는 사실 검증기가 아니다. 입력 메시지가 “재고는 100개입니다”라면 StrOutputParser는 그 문장을 문자열로 반환할 뿐 실제 재고를 확인하지 않는다. 따라서 응답 원문을 상품 설명과 대조하고 검토용 초안으로 사용한다.

실제 모델과 모의 모델을 구분한다

OpenAI 기본 경로는 ChatOpenAI다. 선택 Groq 경로는 공식 ChatGroq 통합을 사용한다. 모의 모드는 LangChain의 FakeListChatModel에 고정 응답을 넣는다. 이때 템플릿·체인은 실제 라이브러리로 실행하지만 모델 추론은 일어나지 않는다. 모든 질문에 같은 응답이 나오므로 품질 비교나 실제 모델 성능 증거로 쓸 수 없다.

모델에게 맡기기 전에 Python이 해야 할 일

빈 질문인지, 상품 id가 존재하는지, 문자열 길이가 적절한지는 Python이 정확하게 검사할 수 있다. 이런 확인까지 모델에게 요청하면 불필요한 호출과 불확실성이 생긴다. 확실한 규칙은 코드로 처리하고 자연어 작성은 모델에 맡긴다.

외부 요청의 계약은 {"record_id": "row-001", "question": "질문"}이다. 상품 맥락을 고객이 직접 넘기게 하지 않는다. prepare_input()이 검증된 카탈로그에서 상품을 찾아 맥락을 구성한다. 사용자가 context라는 키를 추가하더라도 그 값을 회사의 상품 데이터처럼 받아들이지 않는다.

입력 상황 Python 처리 모델 호출
정상 상품 id·질문 상품 선택·공백 제거 진행
질문이 빈 문자열·공백 값 오류 없음
question이 None/숫자 값 오류 없음

500자는 수업에서 정한 문자 수 제한이다. 500토큰을 뜻하지 않는다. 한국어 문자 수와 모델 토큰 수는 일치하지 않는다. 앞뒤 공백은 지우지만 숫자·부정 표현·문장 내부 기호를 임의로 삭제하지 않는다.

Python 함수를 Runnable로 감싸기

prepare_input(request, records)는 요청과 카탈로그를 받아 context, question 딕셔너리를 반환한다. LCEL의 주 입력은 요청 하나로 유지하고 카탈로그는 함수가 만들어지는 시점의 값으로 참조한다.

prepare = RunnableLambda(lambda request: prepare_input(request, records))
chain = prepare | get_prompt() | model | StrOutputParser()

lambda는 입력 하나를 받는 작은 래퍼다. 여기서 모델이 적절한 상품을 스스로 검색하거나 도구를 선택하는 것이 아니다. 지정한 record_id를 Python이 명시적으로 찾는다. 단순한 명시적 선택, 임베딩 검색, LLM 도구 선택은 서로 다른 동작이다.

전처리에서 예외가 생기면 뒤의 프롬프트·모델은 실행되지 않는다. 이렇게 하면 없는 상품에 대해 모델이 그럴듯한 답을 만드는 대신 입력 오류를 알려 줄 수 있다. 형식 검증만으로 모든 보안 요구가 충족되는 것은 아니지만, 최소한의 책임 경계를 만든다.

원문과 모델 맥락을 분리한다

원문은 가공 없이 보존하고, 모델에 전달할 필드만 product_context()에서 고른다. 이번에는 record_id, title, category, description만 쓴다. 원문 price, image를 없애는 것이 아니라 생성 근거에 포함하지 않는 것이다.

정보를 제외하면 모델의 답변 가능 범위도 좁아진다. 가격을 물었을 때 정보가 없다고 말하는 것이 올바른 동작일 수 있다. 모델이 대답을 많이 하는 것과 근거가 맞는 것은 다르다.

from langchain_core.runnables import RunnableLambda
from langchain_core.output_parsers import StrOutputParser
from app.catalog import find_product, product_context
from app.prompts import get_prompt


def prepare_input(request, records):
    if not isinstance(request, dict):
        raise TypeError("요청은 dict여야 합니다.")
    question = request.get("question")
    if not isinstance(question, str) or not question.strip():
        raise ValueError("question은 공백이 아닌 문자열이어야 합니다.")
    question = question.strip()
    if len(question) > 500:
        raise ValueError("질문은 500자 이내로 입력하세요.")
    record_id = request.get("record_id")
    if not isinstance(record_id, str):
        raise ValueError("record_id가 필요합니다.")
    product = find_product(records, record_id)
    # 고객이 넘긴 context는 사용하지 않고 카탈로그에서 직접 구성한다.
    return {"context": product_context(product), "question": question}


def build_chain(model, records, version="designed"):
    prepare = RunnableLambda(lambda request: prepare_input(request, records))
    return prepare | get_prompt(version) | model | StrOutputParser()

LCEL의 batch는 공급자의 별도 할인형 Batch API가 아니다. 목록을 넘겼다고 세 문의가 요청 하나로 합쳐지지 않는다. 이번 실습은 가방·재킷·외장 드라이브의 세 상품 질문을 처리한다. 각 질문은 해당 상품의 설명만 받는다.

동시성과 항목별 실패

기본 batch 구현은 병렬 처리할 수 있다. 강의실에서 여러 학생이 같은 조직 한도를 사용하면 짧은 시간에 호출이 몰릴 수 있다. max_concurrency=1로 학생 프로그램 안의 동시 요청을 제한한다. 이것이 전체 강의실의 전역 호출 제한은 아니다.

return_exceptions=True를 주면 항목의 오류가 결과 목록에 예외 객체로 들어올 수 있다. 결과와 입력의 순서를 맞춰 어느 상품 질문이 실패했는지 표시한다. 다만 이미 시작한 다른 요청을 모두 취소하는 회로 차단기는 아니다. 계정 한도 오류가 나면 수업에서 추가 실행을 멈추고 상황을 확인한다.

스트리밍의 의미

화면에 문자열 조각이 차례로 보이면 사용자는 처리 진행을 확인할 수 있다. 전체 생성 시간이 줄거나 총비용이 줄었다는 뜻은 아니다. 청크 하나가 항상 단어·토큰 하나인 것도 아니다. 코드에서는 각 조각을 바로 출력하면서 동시에 목록에 모아, 끝났을 때 합친 문자열을 보고서에 저장한다.

전체 입력을 기다리는 RunnableLambda가 모델 뒤에 있으면 스트리밍 표시가 지연될 수 있다. 이번 전처리는 모델 앞에서 짧게 끝나므로 맥락 구성 이후 모델 출력을 받을 수 있다. 실행한 chain의 모든 구간이 스트리밍을 그대로 전달하는지 살펴야 한다.

import hashlib
import time
from langchain_core.output_parsers import StrOutputParser
from app.catalog import read_catalog
from app.cli import parser
from app.config import Settings
from app.providers import make_model, friendly_error
from app.pipeline import prepare_input, sample_requests
from app.prompts import get_prompt
from app.report import save_report

def main():
    p = parser(); p.add_argument("--repeats", type=int, default=1, choices=[1,2,3]); args = p.parse_args()
    records = read_catalog(args.data); settings = Settings.read(args.mock); model = make_model(settings)
    rows = []; stop = False
    for repeat in range(args.repeats):
        versions = ["weak", "role", "designed"]
        versions = versions[repeat:] + versions[:repeat]
        for request in sample_requests(records):
            values = prepare_input(request, records)
            for version in versions:
                started = time.perf_counter(); row = {**request, "version": version, "repeat": repeat+1,
                  "context_hash": hashlib.sha256(values["context"].encode()).hexdigest()[:12],
                  "question_hash": hashlib.sha256(values["question"].encode()).hexdigest()[:12],
                  "prompt_hash": hashlib.sha256(get_prompt(version).invoke(values).to_string().encode()).hexdigest()[:12]}
                try:
                    message = (get_prompt(version) | model).invoke(values)
                    answer = StrOutputParser().invoke(message)
                    row.update(status="ok", answer=answer, characters=len(answer),
                               within_500_chars=len(answer)<=500, usage=message.usage_metadata)
                except Exception as error:
                    row.update(status="error", error=friendly_error(error))
                    stop = getattr(error, "status_code", None) == 429
                row["elapsed_seconds"] = round(time.perf_counter()-started,4); rows.append(row)
                if stop: break
            if stop: break
        if stop: break
    save_report(7, records, rows, args.data, settings,
                notes=["같은 상품·질문·모델을 사용합니다. 문자 수는 의미 품질 점수가 아닙니다."])
    print("기록 수:", len(rows))

if __name__ == "__main__":
    try: main()
    except Exception as error: raise SystemExit(friendly_error(error))

CSV는 csv.DictReader로 읽는다. 쉼표가 질문 안에 있으면 CSV 규칙에 따라 큰따옴표로 묶어야 한다. split(",")로 나누면 문의 내용 때문에 열이 깨질 수 있다. Windows Excel의 BOM을 고려해 utf-8-sig를 사용한다.

가공 표본의 id는 row-001 형식이고 직접 API 파일에 id가 있으면 api-1 형식이다. 데이터 파일을 바꾸면 CSV의 id도 그 파일의 실제 목록에 맞춰 바꿔야 한다. 행 순번이 같은 상품이라는 보장도 파일 버전이 같을 때만 성립한다. 출처 파일과 해시를 같이 남기는 이유다.

오류를 항목별로 분리한다

없는 상품이나 빈 질문은 해당 문의만 오류로 기록한다. 정상 문의 결과를 지우지 않는다. 429는 계정 단위 제한일 수 있어 다음 행의 호출을 중단한다. 처리하지 못한 행이 남을 수 있으므로 선택 수와 성공/오류 수를 함께 확인하고, 원인을 해결한 뒤 필요한 대상만 재실행한다.

실습 코드는 같은 경로의 outputs/drafts.jsonl, reports/s08_report.html, reports/s08_report.json을 덮어쓴다. 이전 결과를 보존하려면 실행 전에 복사하거나 캡처를 별도 이름으로 저장한다. 실제 서비스라면 요청 id·중복 처리·발송 승인·원자적 저장 같은 요구를 더 설계해야 한다. 여기서는 자동 발송하지 않는다.

import csv
import json
from pathlib import Path
from app.catalog import read_catalog
from app.cli import parser
from app.config import ROOT, Settings
from app.providers import make_model, friendly_error
from app.pipeline import build_chain, sample_requests
from app.report import save_report

def main():
    p = parser(); p.add_argument("--input", type=Path); p.add_argument("--limit", type=int, default=3, choices=range(1,6)); args=p.parse_args()
    records=read_catalog(args.data)
    if args.input:
        with args.input.open(encoding="utf-8-sig",newline="") as f:
            reader=csv.DictReader(f)
            if not reader.fieldnames or not {"record_id","question"}<=set(reader.fieldnames):
                raise ValueError("CSV 헤더는 record_id,question을 포함해야 합니다.")
            requests=[]
            for i,row in enumerate(reader):
                if i>=args.limit: break
                requests.append(row)
    else: requests=sample_requests(records)[:args.limit]
    settings=Settings.read(args.mock); chain=build_chain(make_model(settings),records); rows=[]
    for request in requests:
        try: row={**request,"answer":chain.invoke(request),"status":"ok"}
        except Exception as error:
            row={**request,"error":friendly_error(error),"status":"error"}; rows.append(row)
            if getattr(error,"status_code",None)==429: break
            continue
        rows.append(row)
    out=ROOT/"outputs/drafts.jsonl"; out.parent.mkdir(exist_ok=True)
    out.write_text("".join(json.dumps(row,ensure_ascii=False)+"\n" for row in rows),encoding="utf-8")
    save_report(8,records,rows,args.data,settings)
    print("성공",sum(x["status"]=="ok" for x in rows),"/ 오류",sum(x["status"]=="error" for x in rows))
    print("데이터 결과:",out)

if __name__=="__main__":
    try: main()

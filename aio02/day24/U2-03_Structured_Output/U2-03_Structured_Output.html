CSV 한 행에서 응답 계약 찾기

은행의 전화 캠페인 기록을 다른 시스템으로 넘긴다. 수신 시스템은 통화 시간을 초 단위 정수로 읽고, 이전 캠페인 결과가 미상인 행도 보관한다. 이번 교안에서는 변환 규칙이 명확한 기록을 사용하므로 모델이 값을 정확하게 옮겼는지 프로그램으로 확인할 수 있다.

필드와 단위 읽기 10분 · 원본 추출 20분 · 두 행 비교 20분

동작 원리

CSV 읽기와 형 변환의 시점을 구분한다. csv.DictReader는 헤더를 키로 쓰고 셀을 문자열로 읽는다. 원본에서 79는 문자 두 개다. 대상 시스템에 보낼 때 정수 79로 바꾼다. age와 y는 이 작업에 필요하지 않아 요청에서 제외한다.

구현과 데이터 변화

rows = read_rows("bank")
row = project("bank", rows[0])
# {'duration': '79', 'campaign': '1', 'poutcome': 'unknown'}

read_rows는 세미콜론으로 열을 나누고 행 목록을 반환한다. project는 duration, campaign, poutcome만 담은 사전을 만든다. CLI의 행 번호는 1부터 시작하므로 --row 1은 rows[0]을 읽는다.

직접 실행

python main.py inspect --row 1
python main.py inspect --row 2

결과 읽기

두 실행의 input을 나란히 연다. 1행은 79초·1회·unknown, 2행은 220초·1회·failure다. csv.DictReader에서 delimiter를 기본값으로 두면 헤더 전체가 한 열이 된다. 열을 찾을 수 없을 때는 먼저 구분자를 확인한다.

키의 존재와 값의 타입 설계하기

스키마는 출력 객체가 어떤 키와 값을 허용하는지 표현한다. 필수 키와 null 허용 여부를 따로 결정하면 수신 시스템은 모든 행에서 같은 키를 읽을 수 있다.

계약 작성 15분 · 스키마 생성 20분 · null과 누락 비교 15분

동작 원리

properties는 각 키의 규칙을 정의하고 required는 반드시 있어야 하는 키를 열거한다. additionalProperties를 false로 두면 정의 밖의 키를 거부한다. previous_result는 문자열 세 값 또는 null을 허용한다. 실제 미상 값은 null이며, 문자열 "null"은 허용 목록 밖이다.

구현과 데이터 변화

class Contact(Contract):
    duration_s: int
    contacts: int
    previous_result: Literal["success", "failure", "other"] | None

schema = Contact.model_json_schema()

Contact는 부모 클래스의 strict=True와 extra='forbid'를 물려받는다. previous_result에 기본값을 주지 않았으므로 필수 키다. 생성된 anyOf의 첫 분기는 문자열 enum, 둘째 분기는 null이다. JSON 측 required 배열에 필드명이 있는지 함께 확인한다.

직접 실행

python main.py schema
python main.py diagnose

결과 읽기

schema의 required 세 항목을 입력의 세 열과 연결한다. diagnose에서 원본 변환은 통과하고 키 삭제는 missing이 된다. 복사한 코드에서 previous_result에 = None을 붙여 schema를 다시 출력하면 required가 달라진다. 공급자 호출 전 기본값을 원복한다.

프롬프트만 사용한 응답 측정하기

이전 차시의 프롬프트 작성법으로 JSON 한 개를 요청한다. 같은 입력·같은 명세로 다음 차시의 요청과 비교하기 위해 공급자와 행 번호를 고정한다.

비교 조건 설정 10분 · 두 행 호출 25분 · 응답 해석 15분

동작 원리

일반 텍스트 생성에서는 스키마를 메시지에 적어도 API가 그 스키마를 출력 설정으로 받지는 않는다. 모델이 정확하게 응답할 수도 있다. 코드 블록을 덧붙이면 내부 JSON이 맞아도 응답 전체를 JSON 문서로 읽는 단계에서 오류가 난다.

구현과 데이터 변화

raw = call_api(provider, prompt, cls, mode, report)
parsed = cls.model_validate_json(raw)
report["parsed"] = parsed.model_dump()

generate는 변환 규칙, 대상 스키마, 입력 행을 한 메시지로 조립한다. call_api가 돌려준 문자열 전체를 model_validate_json에 전달한다. raw에는 수신한 본문, parsed에는 검증을 통과한 딕셔너리가 남는다. 모델이 반환한 마크다운을 임의로 제거하지 않아 원래의 형식 준수 여부를 관찰할 수 있다.

직접 실행

python main.py plain --provider groq --row 1
python main.py plain --provider groq --row 2

결과 읽기

runs에서 입력·실제 모델·finish·raw·status를 확인한다. 정상인 경우에도 그대로 기록한다. 두 행만으로 공급자 성능을 일반화할 수 없으므로 다음 차시에서는 각 행을 같은 조건으로 재실행한다.

API 요청에 JSON Schema 전달하기

같은 메시지를 유지하면서 API 요청 본문에 스키마를 추가한다. 출력 구조를 제약한 뒤, 값을 원본과 따로 대조한다.

요청 구조 해설 15분 · 두 행 재실행 20분 · 방법별 비교 15분

동작 원리

Groq와 OpenAI의 호환 Chat Completions 경로에서는 response_format.type을 json_schema로 지정한다. json_schema 안의 strict는 지원 모델에 스키마 제약을 요청한다. json_object 모드는 JSON 문법을 요구할 때 쓰며 개별 필드 계약은 별도로 필요하다. Gemini 경로는 generationConfig에 JSON MIME 타입과 스키마를 전달한다.

구현과 데이터 변화

body["response_format"] = {
    "type": "json_schema",
    "json_schema": {"name": cls.__name__, "strict": True,
                    "schema": cls.model_json_schema()}
}

이 블록에서 cls는 선택된 Pydantic 클래스다. 구현 함수 call_api의 같은 인자는 schema_type이다. API가 지원하는 키워드가 제한될 수 있어 이 실습은 객체·정수·문자열·enum·null 중심으로 설계했다. 응답을 받으면 종료 사유를 먼저 읽고 정상적으로 끝난 본문만 파서로 넘긴다.

직접 실행

python main.py strict --provider groq --row 1
python main.py strict --provider groq --row 2

결과 읽기

3차시 두 기록과 행별로 비교한다. 시도 수, 정상 종료 수, schema_ok 수, source_ok 수를 각각 센다. 429로 공급자가 전환된 행은 실제 모델 이름을 표시한다. HTTP 400이면 모델의 strict 지원과 스키마를 확인하고 동일한 설정으로 재시도한다.

LangChain에서 Pydantic 객체 받기

동일한 Contact 클래스를 LangChain에 전달한다. 모델 호출 결과에서 원문 메시지와 파싱된 Python 객체를 각각 꺼내 본다.

래퍼와 반환 타입 15분 · 실제 호출 20분 · HTTP 결과 대조 15분

동작 원리

with_structured_output은 입력을 받으면 모델 호출과 파싱을 수행할 Runnable을 만든다. 실제 네트워크 호출은 invoke에서 일어난다. method='json_schema'로 공급자 구조화 출력을 지정하고 include_raw=True로 AIMessage, 파싱 결과, 파싱 오류를 함께 받는다.

구현과 데이터 변화

chain = llm.with_structured_output(
    schema_type, method="json_schema", strict=True, include_raw=True)
reply = chain.invoke(prompt)
parsed = reply["parsed"]

이 차시의 llm은 ChatOpenAI다. parsed가 유효한 Contact이면 parsed.contacts를 정수로 읽을 수 있다. main.py는 파싱 오류·종료 사유를 점검한 뒤 model_dump_json()으로 공통 검증 경로에 연결한다. 패키지 설치와 OPENAI_API_KEY가 필요하며 두 명령 모두 유료 요청이다.

직접 실행

python main.py strict --provider openai --row 2
python main.py chain --provider openai --row 2

결과 읽기

두 기록의 requested_model과 input이 같은지 확인한다. 디버거에서 invoke 다음 줄에 멈추고 type(reply['raw'])와 type(reply['parsed'])를 확인한다. 파싱에 실패하면 parsing_error와 raw를 먼저 읽는다. 반환 객체가 없으면 해당 행을 저장 대상으로 사용하지 않는다.

형식 오류와 원본 불일치 진단하기

실제 1행에서 한 필드씩 바꾸어 검증기를 실행한다. API 호출 없이 오류 위치와 거부 사유를 반복해서 관찰한다.

검증 경계 해설 10분 · 오류 재현 25분 · 원본 대조 15분

동작 원리

JSON 파싱은 문법을, Pydantic은 필수 키·타입·허용값을, reference와의 비교는 실제 원본 일치를 검사한다. 정수 2는 contacts의 타입 규칙을 만족한다. 그러나 원본이 1이면 적재할 값으로 쓸 수 없다. 이 비교가 가능하도록 원본 변환 규칙을 모델과 독립적으로 구현한다.

구현과 데이터 변화

base = reference("bank", row).model_dump()
changed = {**base, "contacts": base["contacts"] + 1}
value = Contact.model_validate(changed)
matches_source = value.model_dump() == base

diagnose는 원본을 유지하고 사본 한 곳만 바꾼다. ValidationError.errors()에서 loc는 오류 위치, type은 분류 코드다. 다른 정수를 넣은 경우 예외 없이 통과하므로 dict 비교 결과까지 읽어야 한다.

직접 실행

python main.py diagnose --row 1
python main.py diagnose --row 2

결과 읽기

실행 기록에서 missing, int_type, literal_error, extra_forbidden을 해당 필드와 연결한다. 다른 정수 항목은 ‘형식 통과 / 원본 불일치’가 된다. 두 행에서 previous_result의 실제 값이 달라도 검증 규칙은 같다.

호출 중단과 한도 초과 처리하기

인증 오류, 사용 한도, 응답 거절, 출력 중단은 복구 방법이 다르다. 한도 초과일 때만 현재 행을 OpenAI에 한 번 전달한다.

실패 분류 15분 · 다른 공급자 호출 20분 · 실행 이력 읽기 15분

동작 원리

HTTP 429는 요청 빈도나 할당량 관련 제한을 뜻하며 잔여 무료량을 특정하지 않는다. generate는 Groq·Gemini의 HTTP 429만 잡아 동일한 prompt와 스키마로 유료 OpenAI를 호출한다. 인증 실패와 잘못된 스키마는 키나 요청 본문을 수정해야 한다.

구현과 데이터 변화

except HTTPError as exc:
    report["attempts"][-1]["http_status"] = exc.code
    if exc.code != 429 or provider not in ("groq", "gemini"):
        raise
    report["fallback"] = f"{provider} HTTP 429 → OpenAI"
    raw = call_api("openai", prompt, cls, mode, report)

call_api는 공급자별 종료 사유와 본문을 보관한다. 일부만 생성된 JSON을 이어 붙이지 않는다. 정상 종료한 새 응답을 처음부터 검증한다. OpenAI 키가 없거나 전환 호출도 실패하면 status=error와 원인을 남긴 뒤 종료한다.

직접 실행

python main.py strict --provider gemini --row 2
python main.py strict --provider groq --row 2

결과 읽기

정상 실행에서는 attempts에 한 공급자만 남는다. 실제 429가 발생한 기록에서는 첫 시도의 http_status, fallback, 마지막 시도의 actual_model을 읽는다. 실패가 발생하지 않은 수업에서는 사용 한도를 소진하지 않고 예외 분기 코드를 추적한다.

공개 데이터 원본과 응답 대조하기

Bank Marketing Dataset의 서로 다른 두 행으로 최종 실행 기록을 작성한다. 데이터명, 원본 링크, 파일 해시와 행 번호를 함께 남겨 같은 입력에서 결과를 재현한다.

원본 확인 10분 · 두 행 처리 25분 · 증빙 저장 15분

동작 원리

1행과 2행에 동일한 계약을 적용한다. duration 값은 각각 79와 220이며, previous_result는 첫 행에서 null, 다음 행에서 failure가 되어야 한다. 스키마 준수와 원본 값 일치를 각각 확인한다.

구현과 데이터 변화

parsed = cls.model_validate_json(raw)
if parsed != reference(dataset, row):
    raise ValueError("원본 대조 실패")

generate는 모델 출력에서 만든 객체를 reference가 원본 행으로 만든 객체와 대조한다. write_report는 실행별 HTML과 JSON에 데이터명, URL, 해시, 입력 행을 함께 기록한다.

직접 실행

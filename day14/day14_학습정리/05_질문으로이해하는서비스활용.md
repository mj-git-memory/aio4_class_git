# 질문으로 이해하는 Redis·세션·실제 서비스 활용

대화에서 질문한 개념과 활용 사례를 정리했습니다. 설치 실패·환경 설정 누락 등 오류 관련 질문은 포함하지 않습니다. 아래의 채용 사이트는 설계 예시이고, 카카오톡·네이버 사례는 사용자가 아는 서비스를 빌린 가정입니다. 해당 회사의 실제 내부 기술 구성을 확인한 내용은 아닙니다.

## 1. Redis와 Docker는 어떤 관계인가요?

**Redis는 데이터를 저장하는 프로그램이고, Docker는 Redis 같은 프로그램을 컨테이너에서 실행하고 관리하는 도구입니다.**

```text
Dockerfile → 이미지 → 컨테이너
만드는 설명서   실행 패키지   실제 실행 공간
```

Docker로 이미지를 만들 수도 있고, 이미 만들어진 Redis 공식 이미지를 받아 컨테이너를 만들 수도 있습니다. 이 수업은 후자입니다.

```text
내 Mac
├─ Python 프로그램: 데이터를 저장·조회하도록 요청
└─ Docker
   └─ kdt-redis 컨테이너
      └─ Redis 서버: 실제 요청 처리
```

`redis-server`는 서버 프로그램, `redis-cli`는 터미널에서 서버에 명령을 보내는 클라이언트 프로그램입니다. CLI는 Command Line Interface로 글자로 명령하는 방식을 뜻합니다. Python에서는 `redis` 패키지가 클라이언트 역할을 합니다.

### 질문했던 명령어 빠르게 복습

다음 명령은 Mac 터미널에서 사용합니다. 실행 중인 컨테이너가 필요합니다.

| 명령 | 뜻 |
|---|---|
| `docker exec kdt-redis redis-cli PING` | Redis 응답 확인. 정상 시 `PONG` |
| `docker exec kdt-redis redis-server --version` | 컨테이너에 설치된 Redis 프로그램 버전 확인 |
| `docker exec -it kdt-redis sh` | 컨테이너의 셸에서 직접 명령 입력 |
| `docker exec -it kdt-redis redis-cli` | Redis 명령을 계속 입력하는 대화형 CLI 열기 |
| `docker stop kdt-redis` | 컨테이너 중지 |
| `docker start kdt-redis` | 중지된 기존 컨테이너 시작 |
| `docker restart kdt-redis` | 컨테이너 중지 후 재시작 |
| `docker ps` | 실행 중인 컨테이너 목록 |
| `docker ps -a` | 중지된 것을 포함한 전체 목록 |
| `docker ps -al` | 가장 최근에 생성한 컨테이너 하나 |

`exec`는 실행 중인 컨테이너 안에서 추가 명령을 실행합니다. `-i`는 입력을 열어 두고, `-t`는 터미널을 할당합니다. 셸이나 Redis CLI에서 `exit`를 입력하면 그 접속 프로그램만 끝나며 Redis 서버는 계속 실행됩니다.

Redis CLI 안에서 다음을 입력할 수 있습니다.

```redis
SET day14:cli:message hello
GET day14:cli:message
TTL day14:cli:message
```

`SET`은 저장·덮어쓰기, `GET`은 조회, `TTL`은 남은 만료시간 확인입니다. TTL이 `-1`이면 만료시간 없음, `-2`이면 키가 없습니다. Mac 터미널에서 한 번만 보낼 때는 `docker exec kdt-redis redis-cli SET day14:cli:message hello`처럼 붙여 씁니다.

생성·삭제를 포함한 전체 명령은 [04 실행 방법](04_실행과오류해결.md), 자료형별 함수는 [03 함수 문법](03_함수와문법.md)에 정리되어 있습니다.

## 2. Redis는 언제 사용하나요?

**반복해서 읽는 데이터를 공유하거나 일정 시간만 보관할 때** 유용합니다.

| 상황 | 예시 | 얻는 이점 |
|---|---|---|
| 반복 조회 | 인기 채용공고 검색 결과 | DB나 외부 서비스의 반복 조회 부담 감소 |
| 로그인 유지 | 세션 ID와 사용자 ID 연결 | 여러 서버가 같은 세션 정보 확인 |
| 임시 데이터 | 3분짜리 인증번호 | TTL로 자동 만료 |
| 호출 횟수 관리 | 사용자별 분당 분석 요청 횟수 | 짧은 시간 구간의 카운터 공유 |
| 순위 | 인기 공고·게임 점수 | 점수 기반 정렬 자료형 활용 |
| 작업 전달 | 오래 걸리는 분석 작업 대기열 | 요청 접수와 실제 작업 분리 가능 |

요청 횟수 제한에는 증가와 만료를 일관되게 처리하는 설계가 필요하고, 작업 대기열에는 재처리·실패 복구 설계가 필요합니다. day14는 이런 기능을 구현한 코드가 아니라 세션·캐시·대화 기록 중심의 기초 실습입니다.

작은 프로그램은 Python 변수나 SQLite만으로 충분할 수 있습니다. Redis를 추가하면 서버 운영·네트워크 통신도 생기므로 모든 조회가 자동으로 빨라지는 것은 아닙니다.

## 3. 카카오톡 같은 메신저에서도 쓸 수 있나요?

활용할 수 있습니다. 다만 다음은 **메신저를 만든다고 가정한 예**입니다.

### 접속 상태

친구의 접속 상태를 보여주는 기능이 있다면 Redis에 상태를 짧게 저장하고 앱이 계속 갱신하도록 만들 수 있습니다. 갱신이 끊기면 TTL이 만료되어 연결 상태를 다시 판단하는 식입니다. 마지막 갱신 시점만으로 실제 접속 상태를 완벽하게 알 수 있는 것은 아닙니다.

### 최근 대화

```text
원본 DB: 오래 보관할 전체 대화
Redis: 빠른 조회를 위한 최근 대화 사본
휴대폰 저장소: 앱에서 빠르게 보여줄 대화·사진 일부
```

이처럼 저장소를 나누면 Redis의 최근 대화가 없어져도 원본에서 다시 가져올 수 있습니다. day14의 `main8.py`가 원본과 캐시를 분리하는 연습입니다. 실제 메신저의 송수신·읽음 확인·암호화는 이 코드에 없습니다.

## 4. 네이버 같은 쇼핑 서비스에서는요?

로그인 세션이나 자주 조회하는 상품 정보에 활용하는 구조를 생각할 수 있습니다. 다음도 실제 네이버 구현을 단정한 설명은 아닙니다.

```text
로그인 → 사용자 확인 정보로 로그인 상태 유지
인기 상품 조회 → 캐시 결과 재사용
주문 생성 → DB에 보관할 거래 기록 저장
사진 조회 → 파일·객체 저장소에서 이미지 제공
```

캐시가 오래된 정보일 수 있으므로 실제 결제에서는 가격·재고를 정확하게 확인하고 거래를 처리하는 절차가 필요합니다. Redis 캐시가 있다는 이유만으로 구매 가능 여부를 확정하지 않습니다.

## 5. 내가 만드는 채용 사이트의 모든 페이지에 Redis가 필요한가요?

**아닙니다. Redis 없이도 로그인·검색·분석·저장 목록·훈련 추천을 구현할 수 있습니다.** Redis는 페이지가 아니라 처리할 데이터와 역할에 맞춰 선택합니다.

| 기능 | 기본 구현 방법 | Redis를 추가한다면 |
|---|---|---|
| 로그인 | 계정 검증 후 세션·토큰 발급 | 세션 저장소로 활용 |
| 공고 검색 | DB·검색 서비스·외부 API 조회 | 같은 검색 조건의 결과 캐시 |
| 적합도 분석 | 프로필과 공고를 외부 모델로 분석 | 같은 분석 조건의 결과 임시 재사용 |
| 저장한 공고 | DB에 사용자 ID와 공고 ID 관계 기록 | 자주 읽는 목록 캐시 |
| 훈련 추천 | 부족 역량과 훈련 정보 비교 | 같은 조건의 추천 결과 캐시 |

“민수가 저장한 공고”는 계속 보관할 사용자 데이터입니다. “민수에게 방금 보여준 추천 목록”은 정책에 따라 다시 만들 수 있는 임시 결과일 수 있습니다. 이 차이가 저장소를 고르는 기준입니다.

## 6. 페이지가 바뀌어도 나라는 것을 기억하려면 Redis가 필수인가요?

필수는 아닙니다. **브라우저가 사용자 확인 정보를 요청에 함께 보내고, 서버가 검증하는 장치**가 있으면 됩니다.

서버 저장 세션을 예로 들면 다음과 같습니다.

```text
로그인 성공
  → 서버가 추측하기 어려운 세션 ID 발급
  → DB 또는 Redis에 “이 ID의 사용자는 민수”라고 기록
  → 브라우저가 세션 ID를 쿠키로 보관

검색·저장 목록 페이지 요청
  → 브라우저가 조건에 맞는 쿠키를 전송
  → 서버가 세션 ID로 사용자 확인
  → 확인된 사용자의 데이터만 처리
```

쿠키는 브라우저가 보관하고 정해진 사이트·경로·보안 조건에 맞는 요청에 보내는 작은 정보입니다. 쿠키가 입장권이라면 서버의 세션 기록은 입장권 확인 장부입니다.

| 방법 | 브라우저가 보관 | 서버가 확인하는 것 | Redis 필수 여부 |
|---|---|---|---|
| DB 세션 | 세션 ID | DB의 세션 기록 | 불필요 |
| Redis 세션 | 세션 ID | Redis의 세션 기록 | 선택한 방식에서 사용 |
| 서명된 쿠키 세션 | 작은 세션 내용과 서명 | 서명·유효기간 | 불필요 |
| 서명된 토큰 | 발급된 토큰 | 서명·만료 등 | 불필요. 취소 정책에 따라 별도 저장소 사용 가능 |

여러 페이지가 각자 “민수”를 기억하는 것이 아니라 서버의 공통 사용자 확인 기능을 사용하는 구조입니다. 화면에서 보내온 사용자 ID를 그대로 신뢰하면 다른 사용자의 데이터에 접근하는 문제가 생길 수 있습니다.

## 7. FastAPI에서는 세션을 어떻게 만드나요?

FastAPI는 웹 요청을 처리하는 프레임워크입니다. Redis는 저장소이므로 서로 대체하는 제품이 아닙니다. **FastAPI가 세션 처리 방식을 구현하고, 필요하다면 저장소로 DB나 Redis를 연결**합니다.

간단한 방법은 Starlette의 `SessionMiddleware`입니다. 이 미들웨어는 **세션 내용을 서명된 쿠키에 담습니다. Redis나 서버 세션 DB에 자동 저장하지 않습니다.** 미들웨어는 각 요청·응답 사이에서 쿠키 확인과 작성 같은 공통 작업을 맡는 기능입니다. [FastAPI 미들웨어 안내](https://fastapi.tiangolo.com/advanced/middleware/), [Starlette 세션 안내](https://www.starlette.io/middleware/#sessionmiddleware)를 참고하세요.

핵심 문법은 다음과 같습니다. 아래는 흐름을 보여주는 코드 조각이며 실제 로그인 화면·비밀번호 검증은 생략했습니다.

```python
import os
from fastapi import FastAPI, Request, HTTPException
from starlette.middleware.sessions import SessionMiddleware

app = FastAPI()
app.add_middleware(
    SessionMiddleware,
    secret_key=os.environ["SESSION_SECRET"],  # 환경에 미리 설정한 비밀키
    max_age=1800,
    same_site="lax",
    https_only=False,  # 로컬 HTTP 실습용. HTTPS 운영에서는 True
)

def remember_user(request: Request, verified_user_id: str):
    # 계정 검증을 마친 사용자 ID만 전달받는다는 전제
    request.session.clear()
    request.session["user_id"] = verified_user_id

def require_user(request: Request):
    user_id = request.session.get("user_id")
    if user_id is None:
        raise HTTPException(status_code=401, detail="로그인이 필요합니다.")
    return user_id
```

`SessionMiddleware`의 서명에 필요한 패키지는 `itsdangerous`입니다. 비밀키는 모든 요청·서버에서 일관되게 유지해야 하며 요청마다 새로 만들지 않습니다.

| 코드 | 역할 |
|---|---|
| `request.session["user_id"] = ...` | 세션 내용에 사용자 ID 기록 |
| `request.session.get("user_id")` | 이번 요청의 세션에서 사용자 ID 읽기 |
| `request.session.clear()` | 세션 내용을 비우고 브라우저 쿠키 삭제 처리 |
| `Depends(require_user)` | 보호할 API 실행 전에 공통 사용자 확인 호출 |

**서명은 암호화가 아닙니다.** 사용자는 쿠키 내용을 읽을 수 있으므로 비밀번호·이력서 원문 같은 민감한 정보는 넣지 않습니다. 또한 쿠키를 지우는 로그아웃은 이미 복사된 쿠키까지 서버에서 즉시 무효화하는 것과 다릅니다. 기기별 세션 취소가 필요하면 서버 측 기록을 두는 설계를 고려합니다.

## 8. 외부 모델 비용을 줄이려고 적합도 결과를 재사용할 수 있나요?

가능합니다. **로그인 상태를 기억하는 세션과 계산 결과를 재사용하는 캐시는 역할이 다릅니다.** 둘을 같은 수명으로 묶어도 되는지 먼저 결정하면 됩니다.

```text
민수의 적합도 조회 요청
    ↓
세션으로 민수 확인
    ↓
같은 조건의 분석 결과가 저장되어 있나?
    ├─ 있음 → 기존 결과 반환. 외부 모델을 호출하지 않음
    └─ 없음 → 외부 모델 호출 → 결과 저장 → 반환
```

“같은 조건”은 사용자·공고만 같은 것을 뜻하지 않습니다.

```text
사용자 ID + 프로필 버전 + 공고 ID + 공고 버전 + 분석 방식 버전
```

이력서가 바뀌거나 공고 조건이 바뀌거나 분석 모델·지침이 바뀌면 다시 계산할 필요가 있습니다. 이 조건들을 문자열 키로 만들거나 내용의 해시값으로 구분할 수 있습니다. 해시는 내용으로 만든 식별값으로, 변경 여부를 구분하는 데 쓸 수 있습니다.

분석 중 같은 요청이 동시에 들어오면 중복 모델 호출이 발생할 수 있으므로, 결과 조회만 붙인다고 중복 비용이 완전히 방지되는 것은 아닙니다. 분석 중 상태나 동시 실행 제어가 별도로 필요합니다.

## 9. DB에 안 넣고 세션에 분석 결과를 넣어도 되나요?

가능합니다. 다만 **세션은 저장 장치 이름이 아닙니다. 어디에 담는 세션인지가 중요합니다.**

### A. 브라우저 쿠키 세션에 작은 결과 저장

```python
# request.session은 SessionMiddleware가 준비했다는 전제
request.session["analysis"] = {
    "job_id": 100,
    "profile_version": 3,
    "job_version": 2,
    "analysis_version": 1,
    "score": 85,
    "summary": "SQL 역량 보완 권장",
}

saved_result = request.session.get("analysis")
```

간단한 실습에서는 가능합니다. 위 예시는 한 결과를 저장하므로 다른 공고를 저장하면 기존 값이 덮어써집니다. 재사용 전 공고·프로필·분석 버전이 모두 일치하는지도 검사해야 합니다.

쿠키는 통상 하나당 약 4KB 수준의 제한이 있고 서명·인코딩도 공간을 사용합니다. 긴 보고서나 여러 공고 결과는 적합하지 않습니다. 쿠키는 요청마다 전송되므로 크기가 커지면 통신량도 늘어납니다. 로그아웃·만료·삭제 후 결과도 잃습니다. 사용자가 읽을 수 있는 쿠키에 넣어도 되는 내용인지도 고려해야 합니다.

### B. 서버 메모리에 결과 저장하고 쿠키에는 세션 ID만 보관

```text
브라우저: 세션 ID
FastAPI 서버의 Python 메모리: 세션 ID → 공고별 분석 결과
```

DB·Redis 없이도 가능합니다. 하지만 서버 재시작·개발 서버 자동 재로딩 시 사라지고, 여러 프로세스나 여러 서버가 이 Python 메모리를 자동으로 공유하지 못합니다. 메모리 용량·만료·정리는 직접 관리해야 합니다. 한 서버 프로세스의 실습용 구조와 여러 사용자가 쓰는 운영 구조를 구분해야 합니다.

### C. Redis에 결과 저장

서버 메모리를 여러 프로그램이 공유할 수 있는 별도 저장소에 두는 선택입니다. TTL로 정리하기 쉽지만 서버가 하나 더 필요하고, 보존 여부는 Redis 설정에 달려 있습니다. Redis를 쓴다고 자동으로 재시작 후 복구되는 것은 아닙니다.

### D. DB에 결과 저장

로그아웃하거나 서버를 재시작해도 다시 쓸 수 있도록 보관할 때 적합합니다. 사용자가 “분석 결과 보관함”을 원한다면 단순한 임시 캐시보다 저장할 원본 데이터로 볼 수 있습니다.

| 원하는 동작 | 선택 예 |
|---|---|
| 현재 브라우저 세션에서 짧은 결과 하나 재사용 | 쿠키 세션 |
| 로컬 단일 프로세스에서 긴 결과를 잠깐 재사용 | 서버 메모리 |
| 여러 서버가 일정 시간 결과 공유 | Redis 등의 공유 캐시 |
| 장기간 보관하고 다음 로그인 때도 확인 | DB |

따라서 “DB에 저장하지 않고 로그인 중에만 재사용”도 가능합니다. **결과 크기·민감도·수명·서버 수**에 맞춰 장소를 고르면 됩니다.

## 10. Redis는 로컬 서버에 있나요?

**실행한 위치에 따라 로컬일 수도 있고 외부 서버일 수도 있습니다.** Redis라는 이름이 로컬 저장소를 뜻하지는 않습니다.

현재 수업에서는 내 Mac의 Docker 안에서 실행합니다.

```env
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
```

여기서 `127.0.0.1`은 Python 프로그램이 실행되는 컴퓨터 자신입니다. 실제 인터넷 서비스에서는 FastAPI와 Redis를 서비스 서버에 배치하거나 서로 다른 서버에 배치할 수 있습니다.

```text
사용자 브라우저 → FastAPI 서버 → Redis 서버
```

이 경우 Redis에 저장된 분석 결과는 사용자 브라우저가 아니라 **Redis가 실행되는 서버의 메모리**에 있습니다. 쿠키 세션에 결과를 저장하는 방식과 보관 장소가 다릅니다.

## 11. 큰 서비스는 DB와 Redis를 모두 쓰고, 데이터센터에 저장하나요?

여러 저장소를 함께 사용하는 구조를 생각하면 됩니다. 특정 회사의 실제 채택 제품은 공식 기술 자료로 별도 확인해야 합니다.

| 저장소 | 맡을 수 있는 역할 | 주된 보관 장소 |
|---|---|---|
| DB | 회원·거래·보관할 대화·분석 결과 | 서버의 SSD 같은 저장장치 |
| Redis | 세션·임시 결과·조회 캐시 | 주로 서버 RAM. 설정에 따라 디스크 기록도 가능 |
| 파일·객체 저장소 | 이미지·동영상·이력서 파일 | 저장소 인프라의 저장장치 |
| 브라우저·휴대폰 저장소 | 쿠키·화면용 최근 데이터 | 사용자 기기 |

**데이터센터**는 전원·냉각·통신망을 갖추고 서버를 운영하는 시설입니다. 클라우드도 그 아래에는 실제 데이터센터의 컴퓨터와 저장장치가 있습니다. 서버는 물리 컴퓨터일 수도 있고 그 위에서 실행되는 가상 서버일 수도 있습니다.

```text
사용자 기기
    ↓ 인터넷
서비스 인프라
    ├─ FastAPI 같은 애플리케이션 서버
    ├─ DB 서버
    ├─ Redis 서버
    └─ 파일 저장소
```

서비스 규모와 설계에 따라 한 컴퓨터에 함께 배치하거나 여러 서버에 나누고, 데이터 복제본을 두기도 합니다. 모든 데이터가 한 데이터센터의 한 서버에만 있다고 생각할 필요는 없습니다. 휴대폰이나 브라우저에도 일부 데이터가 남을 수 있습니다.

## 12. 내 채용 서비스에서는 무엇부터 정하면 좋을까요?

다음 세 질문으로 설계를 시작할 수 있습니다.

1. **사용자를 어떻게 확인할까?** 쿠키 세션, DB 세션 등의 방식 선택
2. **무엇을 계속 보관할까?** 계정·저장한 공고·보관할 분석 결과는 DB 등의 원본 저장소 선택
3. **무엇을 잠깐 재사용할까?** 검색·분석·추천 결과의 캐시 위치와 유효기간 선택

예를 들어 “단일 서버에서 기능을 먼저 확인하고, 짧은 분석 결과는 로그인 중에만 다시 쓴다”면 Redis 없는 구조로 시작할 수 있습니다. 반대로 여러 서버가 큰 분석 결과를 공유해야 한다면 공유 캐시가 유용할 수 있습니다. 기능별로 결정하며, Redis가 모든 페이지의 필수 조건은 아닙니다.

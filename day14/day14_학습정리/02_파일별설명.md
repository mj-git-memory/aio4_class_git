# 파일별 설명: 기능을 하나씩 쌓아 올리기

아래 터미널 예제는 **프로젝트 루트 `AIO_4_class`에서 실행**합니다. `sid_실제발급값`은 그대로 입력하는 글자가 아니라 해당 파일이 출력한 실제 세션 ID로 바꿔야 합니다.

## 1. main.py — 유효기간이 있는 데이터 저장

**만드는 기능:** Redis에 데이터를 저장하고 읽으며, 자동 만료와 직접 삭제를 확인합니다. 인증번호나 임시 알림을 만드는 기초입니다.

```text
.env 읽기 → UUID로 고유 키 생성 → Redis PING
→ 만료 없이 저장·조회 → 같은 키를 2초 만료로 덮어쓰기
→ 3초 대기 → 만료 확인 → 다시 저장 → 직접 삭제
```

중요 함수는 `client.set()`, `get()`, `ttl()`, `delete()`입니다.

```bash
python day14/main.py
```

정상이라면 처음 값과 TTL `-1`, 이후 새 값과 약 2초의 TTL, 만료 후 `None`과 `-2`, 삭제 개수 `1`을 관찰합니다. `uuid.uuid4().hex` 덕분에 다른 실행의 키를 덮어쓸 가능성이 매우 낮습니다.

**응용 예:** “택배 조회 결과를 1분 동안만 기억하기”, “3분짜리 인증번호 저장하기”. 인증번호 검증이나 택배 API 자체는 이 코드에 없습니다.

## 2. main2.py / main2_teacher.py — 자료에 맞는 저장 구조 선택

**만드는 기능:** 상태 한 개는 String, 프로필의 여러 항목은 Hash, 순서가 있는 메시지는 List로 다룹니다.

현재 `main2.py`는 String에 `ready`를 저장하고 Hash의 `name`, `level`을 저장·수정·조회합니다. `list_key` 변수는 만들지만 List에 값을 넣는 코드는 아직 없습니다. `time`도 가져오지만 사용하지 않습니다.

```python
client.hset(hash_key, mapping={"name": "hongildong", "level": "basic"})
client.hset(hash_key, "level", "practice")
client.hgetall(hash_key)
```

`hset()`의 반환값은 새로 추가된 필드 수입니다. 기존 `level`만 바꾸면 반환값은 `0`이어도 수정은 성공한 것입니다.

`main2_teacher.py`는 다음을 추가로 보여줍니다.

- `type()`으로 Redis 자료형 확인
- `rpush()`로 세 메시지 저장, `lrange()`로 전체·최근 두 개 조회
- 없는 값의 `None` 반환
- Hash를 `get()`으로 읽을 때의 오류 처리
- `finally`에서 실습 키 세 개를 정리

```bash
python day14/main2.py
python day14/main2_teacher.py
```

**응용 예:** 상품 상태는 String, 상품 속성은 Hash, 최근 알림 목록은 List. 자료형에 따라 사용할 명령도 달라집니다.

## 3. main3.py — 임시 입장권인 세션 관리

**만드는 기능:** 세션을 생성하고, 세션 ID로 사용자를 확인하고, 로그아웃합니다.

```text
create demo-a → 난수 세션 ID 생성 → Redis에 사용자 ID를 60초 저장
get 세션ID   → Redis에서 사용자 ID 조회 → 가상 이름 표시
logout 세션ID → Redis 키 삭제
```

```bash
python day14/main3.py create demo-a
python day14/main3.py get sid_실제발급값
python day14/main3.py logout sid_실제발급값
```

`create`는 `demo-a` 또는 `demo-b`를 받지만 `get`과 `logout`은 사용자 ID가 아니라 **발급된 세션 ID**를 받습니다. 세 명령은 프로그램을 각각 새로 실행하지만 Redis 서버가 연결 고리 역할을 합니다.

주요 도구는 `argparse`, `secrets.token_urlsafe(32)`, `set(..., ex=60)`입니다. 실제 비밀번호 인증은 하지 않습니다.

현재 파일에는 `env_path`를 계산하는 코드가 있지만 그 경로를 전달하는 `load_dotenv(env_path, ...)`는 주석입니다. 실제 실행되는 것은 인자 없는 `load_dotenv()`입니다.

## 4. main4.py — 대화 내용을 다음 응답에 전달

**만드는 기능:** 세션마다 별도 대화 목록을 보관하고 이전 기록을 응답에 활용합니다.

```bash
python day14/main4.py create demo-a
python day14/main4.py chat sid_실제발급값 "내 이름은 민수"
python day14/main4.py chat sid_실제발급값 "내 이름이 뭐야?"
python day14/main4.py history sid_실제발급값
```

두 번째 질문은 `기록에서 찾은 이름: 민수`라는 모의 응답을 만들 수 있습니다.

`chat` 처리 순서:

1. `lesson04:session:세션ID`를 읽어 유효한 사용자인지 확인합니다.
2. `read_history()`가 Redis List의 JSON들을 사전 목록으로 복원합니다.
3. `make_demo_reply(이전대화, 새질문)`가 응답을 만듭니다.
4. 질문과 답변을 각각 JSON 문자열로 바꿉니다.
5. `rpush()`로 질문 다음 답변 순서로 추가합니다.
6. `ltrim(..., -6, -1)`으로 최근 여섯 메시지만 남깁니다.
7. 대화 목록의 TTL을 300초로 갱신합니다.

| 삭제 명령 | 효과 |
|---|---|
| `clear 세션ID` | 대화만 삭제하고 세션 유지 |
| `logout 세션ID` | 세션과 해당 세션 대화 모두 삭제 |

세션은 생성 후 300초 고정이고, 대화 키는 마지막 저장 후 300초입니다. 대화를 해도 세션 수명은 늘지 않습니다. 이 파일은 SQLite 원본이 없어서, 대화가 만료되거나 Redis 데이터가 사라지면 대화를 복원할 수 없습니다.

## 5. main5.py — 원본 장부와 빠른 사본 분리

**만드는 기능:** SQLite에 대화 원본을 두고 Redis에 최근 조회 결과를 60초 캐시합니다.

```bash
python day14/main5.py init
python day14/main5.py history demo-a
python day14/main5.py history demo-a
python day14/main5.py evict demo-a
python day14/main5.py history demo-a
```

처음 또는 캐시 만료·삭제 후에는 `MISS`, 다음에는 `HIT`가 나옵니다. 이미 캐시가 남아 있다면 첫 실행도 HIT일 수 있습니다.

| 함수 | 담당하는 일 |
|---|---|
| `read_settings()` | Redis 주소·포트·SQLite 경로 읽기 |
| `initialize(conn)` | 테이블 생성, 완전히 비어 있을 때 예제 네 행 삽입 |
| `read_source(conn, owner)` | 해당 사용자의 최근 여섯 메시지를 SQLite에서 조회 |
| `cache_key(owner)` | `lesson05:history:demo-a` 같은 캐시 이름 생성 |
| `decode_history(raw)` | JSON 복원 후 구조 검사 |
| `load_history(...)` | 캐시를 먼저 확인하고 없으면 원본으로 채우기 |
| `show_history(...)` | 메시지 번호와 역할·내용 표시 |

**현재 코드의 특징:** SQL이 `ORDER BY id DESC`로 최신순 조회하고 `read_source()`에서 뒤집지 않아서 출력도 최신→과거입니다. `main6.py` 이후는 `reversed(rows)`로 과거→최신 순서로 바꿉니다. 대화 문맥은 보통 과거부터 읽는 순서가 자연스럽습니다.

현재 `DEMO_USERS`의 표시 이름은 홍길동·강감찬이지만 초기 메시지는 민수·지연입니다. 여기서는 예제 데이터가 서로 다르며, 실행 가능한 ID는 여전히 `demo-a`, `demo-b`입니다.

Redis 장애 시에는 원본이 있어도 프로그램이 오류로 종료합니다. 캐시 장애 대체는 뒤의 `main7.py`에서 추가됩니다. `init`은 Redis 통신 없이 가능하지만 설정 함수는 Redis 설정값도 요구합니다.

**응용 예:** 자주 조회되는 주문 목록, 상품 상세 조회 결과를 캐시하기. 이 코드의 `evict`는 캐시만 지우고 원본 대화는 지우지 않습니다.

## 6. main6.py — 새 대화를 저장한 뒤 캐시 갱신

**만드는 기능:** 원본에 대화를 추가하고, 낡은 캐시가 다음 조회에 쓰이지 않도록 합니다.

```bash
python day14/main6.py init
python day14/main6.py history demo-a
python day14/main6.py add demo-a "오늘은 Redis를 배웠어"
python day14/main6.py history demo-a
```

```text
add 요청
  → 기존 버전의 캐시 키 기억
  → SQLite에 질문·모의 답변을 한 묶음으로 저장하고 확정
  → 기존 캐시 삭제
다음 history
  → SQLite 최신 ID로 새 캐시 키 계산
  → 새 키가 없으면 원본에서 복원하여 저장
```

`cache_key(conn, owner)`는 `MAX(id)`를 조회해서 버전 번호로 씁니다. `save_turn()`은 질문과 답변 두 행을 같은 SQLite 트랜잭션에 저장합니다. `invalidate()`는 그다음 이전 캐시를 삭제합니다.

**왜 원본을 먼저 저장하나요?** 사본보다 장부의 기록이 우선이기 때문입니다. 캐시 삭제를 먼저 하면 다른 요청이 아직 수정 전 원본으로 캐시를 다시 만들 수 있습니다. 이 순서와 버전 키는 실습의 단순한 순차 실행에 맞춘 설계이며, 동시 요청 전체의 일관성을 보장하지는 않습니다.

이 버전은 원본 저장 후 Redis 삭제가 실패해도 오류로 종료합니다. 앞서 `원본 저장 완료`가 나왔다면 원본은 이미 저장되었으므로 무작정 같은 `add`를 재실행하면 중복 기록이 생길 수 있습니다.

## 7. main7.py — 캐시 장애와 세션 장애를 다르게 처리

**만드는 기능:** 캐시가 고장 나도 대화 원본은 조회하고, 세션은 확인할 수 없으면 거절하는 정책을 비교합니다.

```bash
python day14/main7.py init
python day14/main7.py history demo-a
python day14/main7.py create demo-a
python day14/main7.py session sid_실제발급값
```

이 파일에서 `history`, `add`, `evict`는 **사용자 ID를 직접 받는 학습 명령**입니다. `create`, `session`만 세션 기능을 따로 확인합니다. 따라서 이 파일의 이력 조회가 세션으로 보호된다고 설명하면 틀립니다.

| 상황 | 처리 |
|---|---|
| 캐시 정상 | `HIT` |
| 캐시 없음·캐시 형식 손상 후 재생성 성공 | `MISS` |
| 캐시 읽기 중 Redis 오류 | SQLite로 대체하고 `BYPASS` |
| 원본은 읽었지만 캐시 쓰기 실패 | 원본 결과 반환, `MISS_WRITE_FAILED` |
| 원본 저장 후 캐시 삭제 실패 | 경고 출력, 새 버전 키로 예전 사본 구분 |
| 세션 확인 중 Redis 오류 | `PermissionError`로 접근 거절 |

원본 DB 자체의 오류는 Redis 캐시로 숨기지 않습니다. 대체할 신뢰할 원본을 읽지 못했기 때문입니다.

**응용 예:** 상품 캐시가 고장 나면 DB에서 읽어 판매를 계속할 수 있지만, 로그인 확인이 안 되면 개인 주문 내역은 보여주지 않는 정책입니다.

## 8. main8.py — 세션·원본·캐시·모의 응답 통합

**만드는 기능:** 세션으로 확인한 사용자의 대화를 원본에 보관하고 최근 이력은 캐시하며, 이전 대화를 응답에 전달합니다.

```bash
python day14/main8.py init
python day14/main8.py create demo-a
python day14/main8.py chat sid_실제발급값 "내 이름은 민수"
python day14/main8.py chat sid_실제발급값 "내 이름이 뭐야?"
python day14/main8.py history sid_실제발급값
python day14/main8.py evict sid_실제발급값
python day14/main8.py history sid_실제발급값
python day14/main8.py logout sid_실제발급값
```

`main8.py`의 `history`는 `demo-a`가 아니라 세션 ID를 받습니다. 내부에서 `require_session()`으로 얻은 사용자 ID만 사용합니다.

`chat`의 실제 호출 순서:

```text
require_session()      사용자 확인
load_history()        최근 이력 조회: 캐시 또는 원본
make_demo_reply()     이전 이력과 새 입력으로 모의 응답
cache_key()           변경 전 캐시 키 기억
save_turn()           SQLite에 질문·답변 저장
invalidate()          이전 캐시 삭제 시도
print()               결과 출력
```

로그아웃은 **세션 키만 삭제**합니다. SQLite 원본과 사용자별 대화 캐시는 유지합니다. 같은 사용자로 새 세션을 만들면 원래 대화를 이어 볼 수 있습니다. `main4.py`는 세션별 메모이고, `main8.py`는 사용자별 원본 대화라는 차이입니다.

`evict` 후에도 세션이 살아 있다면 SQLite에서 대화를 복원합니다. 반면 Redis 전체가 꺼지면 캐시보다 앞선 세션 확인에서 막힙니다. **캐시 장애 대체 코드가 있어도 main8이 Redis 중단 상태에서 새 대화 요청을 통과시키지는 않습니다.**

이 프로그램이 AI 앱의 기초가 되는 이유는 사용자 확인, 문맥 조회, 응답 생성, 기록 저장의 자리를 분리했기 때문입니다. 실제 AI를 연결하려면 `make_demo_reply()`를 모델 호출로 바꾸고 API 키·호출 오류·비용 등을 추가로 다뤄야 합니다. 현재 코드에는 외부 AI API 호출이나 관련 비용이 없습니다.

## 현재 구현을 읽을 때 구분할 점

| 구분 | 기억할 점 |
|---|---|
| DB 공유 | main5~8이 같은 `SQLITE_PATH`를 쓰면 같은 원본 테이블을 공유 |
| 초기화 | `init`은 전체 테이블이 비어 있을 때만 예제를 추가하며 초기 데이터를 매번 덮어쓰지 않음 |
| Redis 분리 | 차시별 `lesson05`~`lesson08` 키 접두사가 달라 캐시는 서로 다름 |
| 최근 기록 | 원본 전체 삭제가 아니라 응답·캐시에 쓸 최근 여섯 메시지만 선택 |
| 보장 범위 | 질문·답변의 SQLite 저장은 묶지만 Redis와 SQLite 전체가 하나의 트랜잭션은 아님 |
| 동시 실행 | 여러 요청의 읽기→응답→저장이 통째로 잠기는 구조는 아님 |

기존 심화 자료: [readme6.md](../readme6.md), [readme7.md](../readme7.md), [readme8.md](../readme8.md). 기존 자료의 일반적인 `main.py` 실행 예는 실제 실습 파일명 `main6.py`~`main8.py`에 맞춰 읽으면 됩니다.
